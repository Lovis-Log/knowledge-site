## 为什么在 RL 之前还要做 SFT

这一讲是训练部分的第一讲。它先回答一个看起来多余的问题：既然强化学习能直接从环境里学，为什么还要先做监督微调？

课堂上给了两个证据：

- **DeepSeek R1-Zero** 尝试直接在基座模型上做 RL，不经过 SFT。结果是回答中英混杂、可读性很差。
- 随后的 **R1** 重新加入 SFT，只用几千条精心构造的示例，先建立一个高质量的起点，再做 RL。

所以 SFT 的定位不是「最终解法」，而是**冷启动**：让模型先学会 agent 的基本形态——怎么发工具调用、怎么在长对话里继续、工具返回长什么样——然后再让 RL 去打磨。

在 Kimi K3 一类公开流程里，顺序是：SFT 初始化 agent 能力 → RL 发展领域专长 → 在策略蒸馏把多个专家合并回一个模型。

## 三种「更新 agent」的方式

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 改上下文窗口 | 对已发生的事保真度高 | 昂贵、噪声大、不决定什么重要 |
| 改外部产物（文件、记忆） | 可编辑、可检索、可迁移、人可读 | 需要被诱导、筛选与维护 |
| 改模型权重 | 推理更快、行为改变更广 | 训练慢且不透明、与模型绑定、不可逆 |

权重更新最特别的地方是：**改一次，之后每次调用都带着新行为，提示词里不需要额外东西**。代价是你看不见权重里发生了什么，也无法把这次改动搬到另一个模型上。

## 一条轨迹在训练时是什么样子

一条 agent 轨迹包含 system、user、assistant、observation 四种行。它的结构是：

```text
[system] [user 问题] [assistant 思考+工具调用] [observation 工具结果]
[assistant ...] [observation ...] ... [assistant 最终回答]
```

训练时，chat template 会把整条轨迹渲染成一个字符串，并记录每个 assistant 片段的起止位置。随后 tokenize，得到一条长 token 序列，同时得到**每个 token 一位的掩码**：

- 助手生成的 token（包括工具调用、最终回答、停止 token）掩码为 1，计算交叉熵损失；
- 系统消息、用户消息、工具观察掩码为 0，只作为条件上下文。

这就是「教师强制」式的模仿学习：模型在训练时看到的是真实历史，而不是自己采样出来的历史。

### 掩码里容易出错的细节

1. **停止 token 必须在掩码内**，否则模型学不会停下来。
2. **end-of-turn 不是一个事件**：它同时意味着结束消息、结束工具调用、结束任务。Kimi K3 的模板把它们拆成不同的特殊 token，让模型更容易学会「何时停」。
3. **推理块是否计入损失**是模型相关的设计。推理往往很长，如果全部计入，会主导损失，模型可能学会长篇思考却做不对下一步动作。Balanced SFT 一类工作会重新平衡推理与工具调用的比例。
4. **模板漂移是致命的**：训练用的模板必须和服务时完全一致，连空白字符都要一致。若服务时在历史里追加了条件式思考块，前面 assistant 轮次的前缀就变了，工具循环会直接失效。

## 轨迹到底教会了模型什么

- 如何写出脚手架能执行的工具调用；
- 如何在对话变长时继续推进；
- 工具返回值应该长什么样——模型应当**等待结果**，而不是自己编造结果；
- 数据里附带的其他习惯：多余的解说、重复命令、某一类解法。

最后一点很重要：**损失会不加区分地复制每一个动作**。一条最终成功的轨迹，中间也可能包含坏习惯。

## 数据从哪里来

两个维度决定数据策略：

| | 保留全部 | 只保留通过验证器的 |
| --- | --- | --- |
| 强模型生成 | 朴素蒸馏 | 大多数 agent SFT（如 SWE-Gym、OpenHands Agent） |
| 模型自己生成 | 自蒸馏（如 MAI） | 专家迭代（后续课程） |

大多数 agent SFT 落在右上角：用强模型跑任务，只保留通过仓库测试的轨迹。原因很直接——强模型写出的轨迹比学生自己采样得更好，而任务自带的验证器又能过滤掉失败的尝试。

如果没有更强的教师模型，可以自蒸馏，或者把重心放到 RL 上——SFT 的上限本质上受教师能力限制。

### 规模会饱和，分布不会

SWE-Gym 的实验显示：固定任务集、只增加采样数量，准确率会上升，但最终会饱和；而且模型越小越早饱和。实验结束时限制他们的是采样算力，不是任务数量。

另一组对比更关键：同样是 10k 数据，继续采样**同一分布**的轨迹（粉色曲线）会逐渐走平；加入**新任务/合成增强**（蓝色曲线）则持续上升。

结论：**把数据变多不如把数据变宽**。课程给的实证建议是混合 4–8 个来源；再宽对特定基准未必有帮助。

### 成功轨迹也可能有毒

假设三条轨迹都通过了单元测试：

- 一条在多数轮次里反复「改一行—重跑测试」；
- 一条在最终补丁里留下了 `print` 调试语句；
- 一条失败后恢复并最终修好。

直接拿来训练，模型会把循环、残留调试代码和最终修复一起学走。常见的廉价过滤器是**按轮数过滤**：OpenHands Agent 的消融发现，丢掉少于 5 轮的轨迹平均最有效。但轮数只衡量「做了多少工作」，不衡量「工作好不好」——一条 4 轮的干净修复可能被丢掉，一条 14 轮的混乱轨迹却会留下。

### 最好的模型不一定是最好的老师

OpenHands Agent 的研究里，当时基准最强的 GPT-5.3 Codex 反而是**最差的教师**：从它蒸馏后提升最小，甚至出现下降。一个可能解释是：它的思考模式与解题方式离学生太远，轨迹虽然正确，却不好模仿。

所以选教师要看「学生能不能学」，而不只看排行榜。

### 任务来源比超参数更重要

同一项研究显示，任务来源对结果的影响最大：SWE-Smith 对 SWE-bench Verified 贡献最大，对 Terminal Bench 贡献较小。**先选对任务来源，再调其他东西**。

## 一个具体的数据取舍问题

课堂给了三条同一任务的轨迹，问该保留哪些：

- A：4 轮干净解决；
- B：长轨迹，先做错一次编辑，测试失败，恢复后解决；
- C：尝试 11 次，但没有产生任何改动。

讨论的结论倾向于 **A 与 B 都保留**。A 教会正确路径，B 教会错误恢复；只保留 A，模型学不会从失败中回来。但 B 也有风险：损失会连错误编辑一起学。C 没有可学的动作，应当丢弃。

## 标准化数据格式

课堂上介绍了作者参与的 Agent Data Protocol。动机很实际：不同数据集用不同格式——网页数据有的用 HTML，有的用无障碍树；不同 agent 的动作表示也不同。若要把 N 个数据集喂给 M 个 agent，需要写 N×M 个转换器。

标准化之后只需要 N+M 次转换：每个数据集转成统一格式一次，统一格式再转成目标 agent 格式一次。统一格式同时保留 HTML 与无障碍树，下游按需选择。

## 实际训练配置与坑

公开技术报告里的真实配置差异很大：

- Nemotron 3 Ultra：把约 294k token 打包成序列，batch 64，学习率衰减；
- MAI 自蒸馏：128k 序列，大 batch，先 warm-up 再衰减；
- K2 Horizon：512k 序列，分三个阶段，在高量子集上衰减学习率。

这些都不是参数高效微调，而是全量训练。

### 打包

对话不截断、不拆分，而是分配给「剩余容量最贴合」的 pack；相同问题不放在同一个 pack 里；pack 之间再打乱。不拆分是为了避免模型学到被截断的轨迹而产生幻觉。

### 混合专家模型的专家路由

在狭窄的 agent 数据上微调 MoE 时，少数专家会吃掉大部分 token。MAI 报告说，监督阶段的负载均衡比 RL 阶段难约一千倍，drop 率设为 15。

## 训练损失不能替代评估

这是本讲最重要的工程提醒。

训练时，模型在**记录好的轨迹**上每次只预测一个动作，历史永远来自真实数据。部署时没有记录，模型自己的每个动作都会改变下一步看到的东西。一旦走到训练数据没覆盖的状态，低损失不再说明任何问题。

所以：

- 同时监控训练损失与评估结果；
- 先确认模型能过拟合 20 条样本，否则 bug 可能在上游；
- 在真实脚手架与可检查结果的任务上评估；
- 谨慎阅读公开数字，有些是「多个脚手架里最好的一个」；
- 划分数据时要与结论匹配：若声称能泛化到新仓库，就按仓库划分，而不是把同一任务的不同 run 分到两边。

### 跨脚手架鲁棒性

轨迹会连**系统约定**一起教给模型。只在 OpenHands 里收集的数据，未必能迁移到 Claude Code 或 Codex。前沿实验室会跨多个脚手架收集数据，避免模型只会用一种工具。

## SFT 与 RL 的分工

| | SFT | RL |
| --- | --- | --- |
| 学习信号 | 每个 token 的目标 | 每条 rollout 一个奖励数 |
| 数据 | 录好的轨迹 | 模型自己的 rollout |
| 需要 | 数据与 GPU | 实时环境、沙箱、可检查奖励 |
| 擅长 | 工具格式、长任务、通用 agent 能力 | 打磨模型已经会尝试的行为、领域专长 |
| 局限 | 被演示的质量与覆盖面限制 | 奖励设计难、成本高 |

三条结论：

1. 完全不做 SFT，基座模型几乎不动（R1-Zero 的教训）；
2. 只做 SFT，达不到 SFT+RL 的水平；
3. 最佳配方往往从一个**没有训练到自己最高分**的 checkpoint 开始 RL，为后续 RL 留出空间。

因此可以把 SFT 理解为：先建立一个足够好的先验，让 RL 有一个值得打磨的起点。

## 本讲结论

- SFT 是 agent 训练的冷启动，不是终点。
- 轨迹被渲染成一条 token 序列，损失只落在助手 token 上。
- 数据来源、过滤方式、任务分布比多数超参数更重要。
- 成功的轨迹也可能包含坏习惯；按轮数过滤是廉价但粗糙的手段。
- 训练损失不能替代评估；部署会走到训练从未见过的状态。
- 先选对任务来源与教师，再谈规模。

## 理解检验

1. 为什么只对 assistant token 计算损失？训练 observation 会带来什么好处与风险？
2. 一条通过了单元测试的轨迹，为什么仍可能不适合作为 SFT 数据？
3. 「扩大采样」和「扩大任务分布」在曲线上表现有何不同？
4. 模板漂移为什么会让工具循环失效？
5. 为什么说 SFT 的上限受教师模型限制？没有更强教师时有哪些替代路径？
