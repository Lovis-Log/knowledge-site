## 核心问题：当单项任务更自动化，瓶颈为何转向人的注意力？

这篇 DeepSeek Harness 团队文章讨论的是架构思想，不是现有产品功能介绍。所给剪藏为英文机器译文，原文自称中文；本笔记按当前提供的英文正文整理，并配套独立英文版。作者署名部分说明文章由 Yujia Qiao 实现系统并撰写，团队共同讨论。

作者观察：单个 coding agent 能越来越独立地工作，但用户同时跟进多个孤立会话时，仍得亲自切换、记住背景、同步决策。把消息入口接进同一个本地会话，并不能自动解决长工具调用阻塞、上下文混杂和设备离线等问题。

Super-agent 因此被定义为一个跨会话持续存在、能并发处理多项任务的实体。四个目标是 **Continuous（交互与上下文连续）、Productive（并发产出）、Proactive（由事件主动触发）、Persistent（长期在线与恢复）**。这些性质来自周围系统的组织，不能只靠一个更长的提示词获得。

本文重组所给资料，不将文章中的演示视为已经独立验证的产品能力。文章没有时间戳，因此不设视频时间轴。

## 一、先理解连续性与吞吐的矛盾

把所有事件送进同一会话，容易保留全局背景，但单个 ReAct 循环一次推进一步；不同任务的细节互相穿插，长操作还会延迟其他请求。

给每个事件新建会话，则可以并发，但失去共同背景。一次任务在群聊开始、在代码评审中改变计划时，两个会话可能各自得到不同版本；多个会话直接回复人，也会让互动失去统一入口。

作者选择两层架构，把“持续对外沟通和全局协调”与“具体执行”分开。

| 层 | 负责什么 | 保留什么上下文 | 关键约束 |
| --- | --- | --- | --- |
| Router | 接收人的输入、分派任务、跟踪跨任务关系、统一回复 | 全局决策、任务摘要与引用 | 不亲自执行任务，甚至可以不给 Bash |
| Worker | 完成单项任务，使用执行工具，汇报结果 | 与任务有关的独立上下文 | 不直接向外部人类渠道回复 |

Router 与常见 Agent Team 的主控不同：它不必深度拆解每项任务，只负责高层分派。一个 Worker 内部可以再组织团队，但这对 Router 是透明的。文章经验是 Router 的工作可能比想象中轻，执行 Worker 更需要强模型；这不是保证所有场景都适用的模型选型定律。

## 二、事件驱动不等于每条消息都调用模型

作者把来自群聊、邮件、日历、评审和 CI 的半结构化事件叫 Trigger。大多数事件没有行动价值，因此设计为两级过滤：

1. **程序 Fast Path**：按照来源、群组、允许名单或“只响应明确请求”等可确定条件，快速丢弃噪声。
2. **语义 Slow Path**：只让通过初筛的候选事件进入模型，由模型结合上下文和提示策略决定是否行动。

稳定规则交给代码，含糊判断交给模型，降低昂贵语义判断的频次。自然语言策略可以提供灵活性，但它不能自动替代硬性的权限控制。

**补充例子**：一个机器人忽略不在允许名单中的群组，是程序判断；判断一条允许群组里的讨论是否值得主动准备修复，是语义判断。把后者做得聪明，不会让前者变得可省略。

## 三、Thread 订阅让后续事件直接找到执行者

Thread 是同一个 PR、邮件链或 IM 话题下连续事件形成的流，不等于一个 Worker 会话。Router 为新任务创建 Worker 后，Worker 订阅相关 Thread。

- **未订阅事件**：由 Router 理解其含义，判断是否启动新任务。
- **已订阅事件**：程序将后续消息直接送到订阅 Worker，免去 Router 逐条转发的模型工具调用。

两者是多对多关系：一个 Worker 可处理多个有关 Thread，一个 Thread 也可通知多个 Worker。当后续消息超出当前任务时，Worker 可以退订或交回 Router 重新分派。Router 仍可看见事件，统一对外回复；**可见**不等于**必须每条都做语义路由决策**。

这与并发修改的关系尤其重要。订阅能让共享 PR 的 Worker 收到相同通知，有机会协调，但不是文件锁、事务或自动无冲突合并的证明。作者仍依靠 Worker 判断和少量跨任务协调。

## 四、把上下文当缓存：Inline、Spill 与 Chain of Recall

将完整事件都塞入上下文会挤占注意力；只给 ID 又会让模型反复查工具。作者借用缓存和编译器思想：

- **Inline**：把很可能马上用到的信息直接放进当前上下文，例如摘要、附近消息和关联对象 ID。
- **Spill**：把超出预算或不常用的全文放在外部，只留下摘要和可读取的引用。
- **局部性**：优先提供时间或语义位置相邻的对象，逐步增加有用信息。

Chain of Recall 则把这个模式应用到对象图。Trigger、Thread、Worker 等都有唯一 ID；读取一个对象时，同时获得下一跳的相关 ID 和摘要，模型可以按需要沿引用继续检索。

**补充微例子**：用户在邮件中问“昨天那个 PR 改成方案 B 了吗？”系统先读邮件 Thread，得到 Worker ID；再读 Worker 的任务摘要，找到关联 PR Thread；最后读评审中改变方案的消息。它不必把昨天所有聊天全文永久留在当前窗口。

这是一种有引用路径的按需恢复，不是无限记忆。引用缺失、摘要遗漏、权限边界和检索决策都可能造成信息丢失。

## 五、主动准备与异步交互解决不同的等待

### 推测执行：用后台计算换取人的等待时间

作者举例：会议邀请到达后，系统先检查冲突、准备背景与回复草稿；问题讨论出现后，系统静默尝试复现和寻找小修复。结果有用才交付，否则保持安静。

这是在确认最终需求之前先做准备，会消耗可能白费的计算。文章称为 speculative execution。补充边界：准备草稿、研究问题与向外发送消息或修改线上状态是不同动作；主动性本身不构成这些外部动作的授权。

### 全双工：长任务运行时仍可接收新指令

同步 `run()` 会让循环等工具完成。文章将长操作改成 `start()`，立即返回 Started；任务完成后再以事件注入结果，也可通过 `stop()` 终止后台操作。

因此，用户可以在工具运行期间改变要求。新的输入仍须等当前模型推理步结束才处理，不是中断一个 token 的计算。还要将取消和新计划真正传递到执行任务；能接收消息不代表执行内容已经自动更新。

多渠道则处理沟通形式：群聊应该简洁、尽量少打扰；PR、邮件和文档可以保留背景、变更与验证证据。Worker 的详细轨迹不直接流向所有外部渠道。

## 六、持续在线：拆开计算、持久状态与执行环境

作者分两步解除单机绑定。

第一步，把 Agent Loop 计算放在可替换、无状态的云容器，把会话和任务状态持久化在数据库。进程重启后恢复状态，不必让同一台机器永远不休眠。

第二步，把执行环境留在原位置，由轻量 daemon 执行命令、返回结果。用户机器上的未提交修改、内网依赖和特定硬件不必全部复制到云端。BYOM 指 Bring Your Own Machine；云端循环可以等某个设备重新上线，再继续需要该设备的工作。

但云端循环在线，不等于离线端点还能执行命令。也不能因为 daemon 不保存会话，就认为该设备无状态：项目文件、凭据与工具链仍然构成有状态的执行环境。

## 七、Watchdog 要监控进度，而不只是进程存活

一个 Worker 没崩溃，却可能反复做无效工作或偏离目标。外部 Watchdog Session 由定时消息驱动，既处理 API 错误、状态恢复等基础设施问题，也判断 Worker 有没有实质进展。

这里的“外部”是相对于被监控主系统的控制循环。它提升了发现和纠偏能力，并不保证自身永不失败。文章提出维护者可以通过自然语言让它解释异常、调整策略；权限设计和变更记录仍需单独考虑。

## 八、实验到底证明了哪一层能力？

作者明确说，实验使用合成负载和简化环境，结果仅具指示性。端到端实验每次约 300 条消息，其中约 20 条是工作请求，各方案运行 5 次。编码任务由消耗时间的模拟工具代替，**没有检验实际写代码的正确率**。图示还说明消息间隔和工作时长缩至四分之一，模型调用时间未缩放。

| 方案 | 完成时间 p50 / p95（分钟） | 每轮全部会话缓存读取 token |
| --- | --- | --- |
| Super-agent | 12.4 / 15.7 | 23.2M |
| 去掉 Pass-through | 12.6 / 15.5 | 31.8M |
| 单会话加 subagent，中性提示 | 20.4 / 29.5 | 6.1M |
| 单会话加 subagent，优先委派提示 | 13.8 / 29.0 | 10.8M |

中性提示组在 5 次运行中没有调用 subagent；委派提示组有 4 次委派。这说明本实验中仅靠提示决定委派，可能有不稳定的长尾，而结构性分工更稳定。它没有证明任何多层结构必然优于所有优化后的单会话系统。

补充计算：Pass-through 把缓存读取从 31.8M 降到 23.2M，相对无直通组减少约 $(31.8-23.2)/31.8\approx27\%$；反过来说，无直通组比完整组多约 37%。分母不同，两种描述不能混用。p95 在这两组几乎相同，不能宣称直通已明显改善任务完成延迟。

Router 压测采用真实路由模型和模拟 Worker：待决策 Trigger 到达率由约每分钟 1 条升至 40 条，平均批量从 1.0 升至 2.8，单请求耗时从 2.5 秒升至 3.9 秒，每决策摊销推理时间从 6.4 秒降至 1.6 秒。后一个量不等于简单用请求耗时除以批量，因为一次决策可能跨多次模型请求。结论是积压合批可能改善吞吐，不是负载越高用户等待必然越短。

## 九、尚未解决的问题与安全边界

原文列出 Router 扩展、无会话交互产品形态、上下文划分与 A2A，以及安全和隐私。A2A 在这里泛指 agent 间沟通，不指某个特定协议。

全局上下文有利于协同，也要求决定哪些人和任务可以共享信息。云端 Agent Loop 持续读取不可信消息，而端点保存代码、文件和凭据，一次提示注入可能跨越到多个设备。作者特别强调：系统需要能使用凭据而不让模型看到凭据的机制。

因此，“云端大脑加本地手脚”不只是部署技巧，还必须处理信任边界。原型并未因拥有 Router、Worker 和 Watchdog 就自动解决这些问题。

## 理解检验

1. **为什么 Router 不应顺手完成每个小任务？**  
参考答案：它承担全局连续交互；执行会重新引入长操作阻塞、上下文污染及依赖即时判断的委派不稳定。小任务成本仍要结合实际负载评估。

2. **Thread 与 Worker 是一一对应吗？**  
参考答案：不是。订阅是多对多；事件流负责组织外界消息，Worker 会话负责执行任务。

3. **Chain of Recall 与把全部历史塞进窗口有什么不同？**  
参考答案：它依靠 ID 和摘要形成引用图，按需逐跳恢复详情；代价是额外检索及可能遗漏，而不是无限长度上下文。

4. **实验能证明代码质量提高吗？**  
参考答案：不能。编码执行被模拟，主要测调度、协调与延迟，并显示更多缓存读取换来更稳定完成时间的权衡。

5. **云端在线是否解决了本地机器离线？**  
参考答案：只解决循环和持久状态的可用性。依赖离线设备的命令仍须等待端点恢复，且端点权限与凭据需要单独保护。
