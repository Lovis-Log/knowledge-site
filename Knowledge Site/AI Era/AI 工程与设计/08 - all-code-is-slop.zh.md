## 每月数千个 PR，质量靠什么守住

Lauren Tan 的开场是一个略带挑衅的举手调查：有多少人看过别人写的代码，心里想“全是垃圾”。她说自己也一样，然后给出这场演讲要证明的事——垃圾可以变成金子。

她的论点不是“Agent 写的代码更好”，而是一个关于工程师角色的判断：**软件工程师的元任务，是在大幅提高产量的同时，维持甚至提高代码质量**。有人把由此形成的工作方式叫“软件工厂”，她更愿意把它归结为一件事——信任。不是盲目信任，而是把 Agent 的环境投资到“你可以相信它会做对”的程度。

这个投资不是免费的。她说自己花了六个月，才到“一个月向生产环境发出几千个 PR、很多是在睡觉时完成的”的状态；她也明确说，后来者会比她快得多。

## 可信度倒金字塔：把信任放进环境

![可信度倒金字塔从架构与 API 开始，依次加入静态约束与测试、运行时与形式验证、文字规则](/images/all-code-is-slop-trust-zh.svg)
*图：Lauren Tan 建议优先投资代码和可执行检查，再为需要判断的事项补充文字规则。*

**作者观点**：她用一个倒金字塔来安排“该往 Agent 环境里投多少时间”。最宽的一层是代码本身——好的 API 设计、架构、重构，以及 lint、类型系统、编译器、各类测试；这些是确定性的，能约束 Agent 的行为，让它默认做对。再往下是验证，包括运行时验证和形式验证，用来找 bug、检查系统必须成立的性质，也用来检验 Agent 是否真的理解了目标。最窄的尖端才是少量文字：rules、skills、`AGENTS.md`，以及那些必须靠判断的东西。

她特别强调顺序：从代码库开始。因为 Agent 的输出由输入决定，而代码库是最大的输入之一。代码里如果留着 workaround、反模式、废弃代码和技术债，下一个 Agent 很可能把它当成“这个仓库的既定写法”照抄。她用花园作比喻：杂草和害虫一旦长起来，会在你意识到之前扩散；所以要让代码库尽可能干净，让 Agent 只抄到好的部分。

由此得出她的核心操作原则：**每次纠正 Agent，先想能不能把它变成确定性检查，而不是往 rules 或 `AGENTS.md` 里再加一行**。写在代码里的约束更可复现，也更值得信任。

| 层 | 手段 | 它主要保证什么 | 它保证不了什么 |
| --- | --- | --- | --- |
| 架构与 API | 目录边界、禁用难以用好的 API、重构 | 错误写法在结构上没有落脚点 | 需求错了、产品判断错了 |
| 静态约束与测试 | lint、类型、编译器、单元/集成测试 | 可枚举的规则与已覆盖的回归 | 没写进规则的坏习惯、环境差异 |
| 验证 | 运行时（DevTools、feature map）、形式验证（TLA+/Lean）、性质测试 | 真实执行路径、状态空间性质、UI 不变量 | 未被建模的流程、规格自身的错误 |
| 文字 | rules、skills、`AGENTS.md` | 传递判断、背景与偏好 | 不可强制执行、会过期、可被拿来辩解 |

这张表是**笔记补充**：原文给的是层级和例子，“能保证什么/不能保证什么”是本稿的归纳。

## 架构与 lint：让错误写法写不出来

### Dune：把“需要有分寸才能用好”的东西禁掉

**原文事实**：Dune 是他们为 Grok Bot 做的客户端框架，技术上不算特别，可以理解成“给 Electron 应用用的 Next.js”。真正有意思的是它把做桌面应用学到的教训编码成了大量约束和 lint 规则。

其中一条教训是：**任何“需要有分寸才能用好”的东西，最后都会生产垃圾**。她举的例子是 React 的 `useEffect`：它有用例，但经常被误用，有人开玩笑说用好它需要博士学位。Agent 并不擅长这种分寸判断。他们的解法是在产品代码里直接禁用，只在 Dune 自己的 API 内部少数地方允许。结果是这类问题被“从类别上消除”，代码审查再也不需要抓它。

### 用目录结构传递上下文

**原文事实**：他们在 Cursor（一个 Electron 应用）上看到过一个反模式：Agent 经常把主线程代码 import 进渲染线程，造成长任务和卡顿。到了 Grok Bot 和 Dune 的应用里，这件事被做得非常约定化：顶层有两个目录，字面就叫 `electron-renderer` 和 `electron-main`，两者之间的 import 被依赖图分析器和 lint 规则禁止。

她的评价很朴素：这类 lint 规则设置起来很简单，但意味着代码审查时少了一件要担心的事。

### 注释为什么会被 Agent 用来辩护

**原文事实**：她观察到 Agent 会用 Markdown——文档、代码注释、rules、skills——来给“没有做对的事”写理由；也会把你的一次小纠正过度放大，当成永远不能破的硬规则。

最典型的案例还是 Cursor。Agent 很喜欢用命令式计时器：`setTimeout`、`requestAnimationFrame`、`requestIdleCallback`，拿它们当快速补丁，去填 VS Code 命令式风格和 React 声明式风格之间的架构冲突。结果是他们的架构选择同时拖慢了客户端和 Agent。做过 JavaScript 性能的人都知道，大量计时器被快速创建和销毁会带来频繁的垃圾回收，进而造成卡顿。

更糟的是，Agent 写了大量注释来解释这些补丁为什么合理。很快计时器到处都是，应用性能明显下降。

所以在 Grok Bot 里，他们决定禁掉 99% 的注释：注释容易过期，人本来也不怎么看注释栏，而且它给了 Agent 一个“因为难做所以绕过去”的逃生口。她认为注释最根本的问题是**不可强制执行**：你想告诉下一个 Agent 不要做某事，但那句话本身不构成任何可验证的约束。

替代方案是 lint 规则给出好的报错信息，直接要求 Agent 去修根因，而不是绕过问题。她把这套做法上升为原则：每次纠正，要么变成确定性检查，要么通过更好的 API 设计和架构把问题从类别上消除。做得足够多以后，代码审查里要看的东西会越来越少；到某个点，你会发现“没什么可审的了”，可以放手让 Agent 合并它们自己的大部分 PR。

## 运行时验证：审查对象从 diff 变成证据

**原文事实**：她的代码审查流程已经缩成“看验证产物”：视频、截图、图表、形式验证。最基础的是运行时验证——说白了就是给 Agent 一种自己运行代码的方式，并让它使用人类开发者也在用的调试工具，比如 Chrome DevTools Protocol。

在运行时验证 skill 里，他们有一个叫 **feature map** 的东西：从用户视角列出应用里所有可用功能的“站点地图”。这样当你说“左边栏那个东西”时，Agent 不需要猜，双方有共享词汇。

他们还在 skill 里封装自定义 CLI，让 Agent 每次都复用同一个 CLI 和 driver。好处是省 token，而且可测试。

**笔记补充**：这一步实际上改变了“审查”的对象。以前审查者读的是代码差异，现在读的是行为证据。代码差异回答“改了什么”，证据回答“改完之后它做了什么”。后者更适合发现“实现和意图不一致”，但也更容易被精心挑选的证据误导，所以证据的生成方式本身要可复现。

## 形式验证与性质测试：能证明什么，不能证明什么

**原文事实**：他们最近开始试形式验证。用 TLA+ 对主要用户流程做模型检查，例如跨多设备、多平台的通知；用 Lean 证明某些算法，比如他们自研的虚拟化库，要检查它不会出现闪烁或抖动。她说整体仍在实验阶段，看起来很有前景，已经借此找到不少 bug，但绝不是银弹，只当作 Agent 环境里的又一层工具。

UI 方面，他们开始用性质测试，库叫 Bombadil，也已经抓到几个 UI bug。

她还做了一个叫 state chart 的 skill，放在自己的插件集 pstack 里，用来从用户视角把状态机可视化；她说把它和验证视频、截图放在一起，更容易审查。

**笔记补充**：形式验证检查的是“你已经写成规格的那部分性质”。TLA+ 擅长的是并发与跨设备状态空间里的不变式，Lean 擅长的是算法层面的定理证明。它们都不能证明“规格本身符合用户想要的东西”，也没有覆盖没有被建模的流程；建模和维护的成本也真实存在。所以它能提高信心，但不能替代运行时测试和人的产品判断。

## 验证成了新的成本中心

**原文事实**：她引用了一条六个月前的推文：作者说自己无法信任 Agent，因为总有微妙的 bug 被合进去；她缺的正是验证流程。六个月后，这位作者说每天 70% 的 token 花在验证上。Lauren 说这与她自己的观察一致——她的大部分 token 也用在验证。

她的判断是：这些技术没有一项是全新的。它们都是很好的软件工程工具，只是在过去“贵得用不起”——难懂、难写、难维护。Agent 把这项成本大幅降低了。她由此说我们正在进入软件测试与验证的黄金时代：可以测试到过去在经济上不划算的程度。形式验证还能帮助你想清楚产品应该怎样工作，以及 Agent 是否真的理解了你的意图。

## 把数字放回语境：3,000、11,000 和 0.5%

**原文事实**：她上个月个人向生产环境交付了 **3,000 个 PR**。她说在此之前，大家并不关心提交量，只关心极少数“编码机器”式的极端高产者；有了 Agent，任何人都可能成为编码机器。

团队层面，Grok Bot 同一个月向生产环境交付了 **11,000 个 PR**。客户端发布节奏也加快了，大约每天切一个稳定版；十月约有 **227 人**至少贡献了一个 PR，其中不少是上下文不多的顺手贡献者。

回滚方面，她说被回滚的 PR 数量在相对比例上反而下降了，稳定在 **约 0.5%**。同时，Grok Bot 的性能没有退步，启动、输入、打开新会话、切换会话都比发布时更快——她提醒听众，它目前仍是 Electron 应用，所以有天花板。

还有一个她用来描述审查量变化的对比：2024 年她去上班，审的是同事写的三个 PR；今天这个数量更像 300。

| 数字 | 口径 | 不能误读成 |
| --- | --- | --- |
| 3,000 PR/月 | Lauren 个人，一个月，高度自动化的环境 | 团队产量，或普通工程师的基准 |
| 11,000 PR/月 | Grok Bot 团队，同一个月 | 全公司、所有仓库的产量 |
| 约 0.5% | 该团队同期被回滚 PR 的相对比例 | 个人指标、事故率，或永久不变的质量线 |
| 227 人 | 十月至少贡献一个 PR 的人数 | 核心团队规模 |
| 每天一个稳定版 | 客户端发布节奏 | 所有产品的发布节奏 |

**笔记补充**：这些数字回答的是“在这套地基上、这个团队、这个月能做到什么”，不是“Agent 普遍能带来什么”。她的六个月爬坡期、团队的产品阶段、Electron 客户端的具体架构，都是数字的背景条件。把它们当成行业基准，会得出错误结论。

## 适用条件：先打地基，再建工厂

**作者观点**：在跳进去建“软件工厂”、把所有能自动化的都自动化之前，先在做每一次纠正时改进代码库。她给的顺序是：先用 lint 规则阻止新的反模式出现，再清理旧的；然后确保验证故事足够强。

她的理由是一个因果链：这些工作本来就是自动化的前提。如果内循环本身在生产垃圾，自动化这个循环只会生产更多垃圾，然后你需要往问题上砸越来越多 token——而 token 很贵。

当地基具备——代码、静态分析、运行时验证、形式验证——很多事才变得可能，你才能在基础上搭自己的工厂。到那时，Grok Bot 的 connectors、routines、Cursor cloud agents 和 projects 可以编排几百甚至几千个 Agent。她举了一个具体例子：每次切新版本，Grok Bot 会自动起一个 Cursor 项目，对整个应用和构建做 fuzz，像真实用户一样使用它来找 bug，然后为每个 bug 开修复 PR，并自动合并。

她马上给了这个例子的前提：**因为代码库已经足够好，PR 默认就是好的**，大部分产品代码不再需要深度人工审查。这不是“自动合并很酷”，而是“自动合并只有在前面所有层都成立时才成立”。

## 理解检验

**1. 为什么“在产品代码里禁掉 `useEffect`”比“在 `AGENTS.md` 里写一句不要用 `useEffect`”更可靠？**

前者是确定性约束，在 lint/编译层面直接阻止，不依赖 Agent 是否读到、记住或正确解释那句话；后者是文字请求，会过期、会被忽略，也可能被 Agent 用注释或规则辩解。她的原则是尽量把每次纠正变成可执行的检查，或者从架构上消除这类写法。

**2. TLA+ 和 Lean 各自检查什么？为什么她说它们不是银弹？**

TLA+ 用于对跨设备通知等主要用户流程做模型检查，检查状态机层面的性质；Lean 用于证明算法性质，例如自研虚拟化库不出现闪烁或抖动。它们只能检查已经被建模的部分，规格本身可能错，建模和维护也有成本，所以只是另一层工具，不能替代运行时测试和人的产品判断。

**3. 3,000、11,000 和 0.5% 分别是什么口径？**

3,000 是 Lauren 个人在一个月内向生产环境交付的 PR 数；11,000 是 Grok Bot 团队同月的 PR 数；约 0.5% 是她在演讲中报告的团队回滚比例。她说比例先前有所下降，随后稳定在约 0.5%。不能把 3,000 说成团队产量，也不能把 0.5% 当成个人指标或全公司指标。
