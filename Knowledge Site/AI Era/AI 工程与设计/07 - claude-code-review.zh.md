## 核心问题：审查的计量单位变了

Claude Code 团队给出的前提很直接：这个产品约九成的代码由 Claude 自己写。代码不是变少了，而是变多了——从六月到九月，合并进 Claude Code 仓库的 PR 数量增至两倍以上，而需要回滚的 PR 占比下降了四成以上。文章要回答的因此不是“还要不要审查”，而是当产量按倍数增长时，人的注意力该花在哪里。

原文把问题重写了一句：与其问“有没有人读过这段代码”，不如问“这次变更可能出什么错，哪一种检查——自动的还是人的——最适合抓住它”。这个替换很关键。前一个问题只能回答“是/否”，后一个问题可以拆成不同的失败模式，再分给不同的层。

审查的位置也随之改变。过去它是终点前的一道门：写完、开 PR、等同事。现在它更接近写作时的拼写检查，大部分例行问题在人被叫来之前已经被 Claude 自己修过至少一轮。人看到的是一个已经过了机器一遍的版本，注意力可以留给方向、架构和真正昂贵的风险。

## 一次变更要过哪几层

![变更先自验，经过 PR 审查和风险审批，在合并队列重跑检查，最后分批上线并监测](/images/claude-code-review-flow-zh.svg)
*图：每道检查在提交、合并与发布过程中的位置。*

| 阶段 | 检查 | 谁执行 | 它主要拦什么 |
| --- | --- | --- | --- |
| 提交前 | 测试、构建、lint、截图比对；新上下文子 Agent 读 diff | Agent | 作者自己就能发现的低级错误 |
| 每个 PR | 必需 CI：lint、类型、跨平台测试、构建打包 | 机器 | 可枚举、可复现的回归 |
| 每个 PR | Claude 代码审查：并行找 bug、验证者投票 | Agent | 语义层面的缺陷与漏改 |
| 每个 PR | 独立安全审查，未关闭的 finding 阻塞合并 | Agent | 安全边界与敏感路径 |
| 每个 PR | 按风险分级的人工审批（0、1 或 2 人） | 分类器 + 人 | 方向、架构、不可逆风险 |
| 合并时 | 合并队列在最新 main 上重跑全部检查 | 机器 | 两个各自通过的 PR 组合后弄坏主干 |
| 合并后 | 内部开关、latest→stable、值班监控 | 人 + 机器 | 漏网的生产问题 |

自验、审查和审批拦截合并前的问题。进入合并队列后，还要检验改动与最新主干能否一起工作。发布监控负责尽早发现前面漏掉的回归。

### 提交前自验：把“看起来做完了”变成可运行的证据

**原文事实**：多数审查现在发生在 PR 出现之前。团队给 Claude 一个能运行的东西——测试、构建，或一张可以对照的设计截图——并要求它展示输出，而不是口头宣布完成。随后一个子 Agent 用全新的上下文再读一遍 diff。UI 变更还会对照设计规范检查；不少工程师在开 PR 前还会跑几个内部 skill，分别找 bug、简化 diff、做端到端验证。

原文引用了 Claude Code 的创建者 Boris Cherny 的判断：给 Claude 一种验证自己工作的方式，可能是拿到好结果最重要的一件事，他估计这会让最终质量提高两到三倍。验证的形式按领域变化，可能是一条 bash 命令、一套测试，也可能是在浏览器或手机模拟器里真的把功能点一遍。

**笔记补充**：这一层买的是返工成本。错误留在作者自己的上下文里时最便宜，因为它还知道当初为什么这么改。但同一会话也有盲区：写代码的 Agent 容易沿用自己的假设，所以“新上下文的子 Agent”不是重复劳动，而是把“作者视角”和“审查者视角”分开。

### AI 审查：先找 bug，再让另一组 Agent 投票

**原文事实**：每个 PR 在人看之前都会过一次 Claude 审查。它同时读 diff、整个仓库和 PR 声明的意图，问三件事：这个改动是否真的解决了它声称的问题、是否符合系统既有结构、是否会弄坏别的地方。修 bug 的 PR 还会被追问根因。

实现上不是“一个模型说一句就算”。多个 Agent 并行找问题，另一组 Agent 对每个 finding 投票，够票才发布；只涉及风格、诊断信息或清理的 finding 会被丢掉。原文说这些过滤器在上线前用自家 PR 做过 A/B 测试。留下的按严重度排序，并标注 Important、Nit 或 Pre-existing——最后这个标签用来区分“这个 PR 引入的问题”和“本来就在那里的问题”。

效果数据来自研究预览上线时：内部 PR 中获得实质审查评论的比例从 16% 升到 54%；超过一千行的 PR 大多能拿到 finding，小 PR 大多干净返回。管理员可以按仓库选 Quick、Standard 或 Deep，Deep 用在“漏一个 bug 的代价高于多花审查时间”的地方。

每条 finding 都必须被回答：要么修，要么在讨论串里写理由关闭。原文提到，Agent 常会在夜里接手修复，作者第二天回来时 PR 已经又过了一轮。

**笔记补充**：投票机制解决的是“召回率与噪音”的平衡，不是正确性证明。它降低的是单个模型误报的概率，不能保证没被报出来的问题就不存在。原文把过滤器拿去做 A/B 测试，说明“噪音”本身被当成产品指标，而不是审查的副产品。

### 硬性检查与安全审查：可枚举的错误交给机器

**原文事实**：必需的 CI 包括 lint、类型检查、各平台测试和构建打包，红色直接阻塞合并。一个典型的 CLI PR 在人看之前可能已经跑过几十项检查。

安全是单独的一遍自动审查。只要 bug 审查或安全审查还有未关闭的 finding，PR 就不能合并；误报可以用一段简短理由关掉讨论串，后续提交真的修好了，finding 会自动消失。

PR 模板要求填写“怎么测的”和“怎么撤销”。Claude 可以代填，但提出这个需求的人要签字确认。

**笔记补充**：CI 和 lint 能拦的是“规则已经写下来的错误”，优势是确定、可复现、不消耗人的注意力；局限也在这里——规则没覆盖的坏习惯、需求本身错了、架构选错了，它都看不见。所以硬性检查越强，越要把人的时间挪到规则管不到的地方。

### 人工审批：按变更的风险，而不是按作者的级别

| 风险层级 | 典型变更 | 需要几个人 |
| --- | --- | --- |
| 低 | 文档、文案、仅内部使用的功能、开关后面的增量改动 | 自动审查与安全检查全绿后可以为零 |
| 中 | 普通产品改动；缓存、自动更新器、系统提示等敏感区域 | 一人 |
| 高 | 最高风险代码，以及一小批永远需要两人的路径 | 两人 |

**原文事实**：是变更本身决定层级，不是作者的身份。一个分类器读 diff 给出风险层级，第二个分类器再判断“即使层级不高，这一个改动是否仍需要另一个人”。有些路径永远要人：代码所有者标记为敏感的路径，以及任何 CI workflow 文件。

只有仓库可信名单上的作者才能走轻路径，名单基本就是拥有这个仓库的团队；其他人即使改的是低风险内容，也需要第二个人批准。Agent 的批准永远不能顶替一个人类名额。反过来，发起这个改动的人要对它负责——如果是人指挥 Agent 写的 PR，指挥者就算作所需审查人之一，和亲手敲代码一样。

批准只覆盖一个具体 commit。如果后面又来了系统无法担保的新提交，比如 Agent 自己推的，或者有人手工解了冲突，批准就要重新给。

**笔记补充**：这套设计有一个隐含假设：风险可以从 diff 的特征预测出来。分类器一定会误判，所以它前面有 AI 审查，后面有安全审查、合并队列和回滚。换句话说，风险分级不是为了做到零误判，而是为了让误判的代价落在更便宜的层。

### 合并队列、渐进发布与回滚

**原文事实**：合并队列会把每个检查在最新 main 上、带着这个改动再跑一遍，避免两个单独通过、合起来坏掉的 PR 进入主干。新行为通常先放在开关后面，只给 Anthropic 员工用；内部的高频使用往往比外部用户更早暴露回归。公开发布先走 latest 通道，stable 通道跟在后面。

最后一层是“尽快发现、尽快撤销”。开关可以不发版就关掉；坏构建直接 revert；团队有每周轮值的 on-call，事故复盘会问“哪一层本该抓住它”。

原文也承认边界：目前还没有在回滚率或事故率上升时自动收紧审批的断路器，工程师希望在做更多“零人工合并”之前先有这个东西。文中一位同事的说法也被保留：放慢速度确实会降低错误率，但很大程度上只是因为你做得更少。

## 三个指标不要混：合并量、回滚比例、事故

| 指标 | 它回答的问题 | 原文给出的数字 | 常见误读 |
| --- | --- | --- | --- |
| 合并量 | 产能有多大 | Claude Code 仓库 6–9 月合并 PR 数增至两倍以上；Anthropic 整个 monorepo 从 5 月约 2,500 次/天到 9 月超过 30,000 次/天 | 把两个仓库的数字当成同一条曲线 |
| 回滚比例 | 被撤销的变更占多少 | 6–9 月需要回滚的 PR 占比下降四成以上 | 把它读成“回滚次数下降”，或当成质量总指标 |
| 事故 | 后果有多严重 | 原文只把它作为护栏，没有给具体数字 | 用回滚率代替事故率 |
| 人工时间 | 人花了多少注意力 | 每个 PR 的人工批准数（中位数与 95 分位）、人工评论数、等待人的时长 | 只看“审批人数”，不看等待与返工 |

**原文事实**：团队用人工批准数、人工评论数和 PR 等人的时长来衡量人的成本；回滚率和事故率是护栏——如果它们上升，说明时间没有被省掉，只是从审查挪到了修复。

假设六月合并 100 个 PR，回滚 10 个，回滚率为 10%。九月如果合并 220 个 PR，回滚率降到 5%，回滚率降了 50%，回滚次数却从 10 次增到 11 次。这是算术示例。原文报告了合并量和回滚比例的相对变化，因此无法从两项变化直接推算绝对回滚数或事故数。

## 让审查收敛：不是每一轮都能带来新信息

**原文事实**：Agent 作者加 Agent 审查者，可以互相忙到天亮。文中举了一个 CLI PR，一夜之间经历了五十多轮审查与修复，最后作者手动叫停。

团队用 git blame 回查审查者反复标记的代码，发现约 59% 是审查者第一轮时就已经在那里的代码。也就是说，它很少在发现“新 bug”，更多是在每一轮多找出几个“旧 bug”。

他们自己也承认把问题弄大了：因为每多跑一轮总能抓到点什么，团队逐渐默认跑好几轮。这在高风险改动上可能值得，但不该成为每个 PR 的默认。

后来改了四件事：三轮之后设上限，要求作者退一步重新考虑方案；前几轮之后只审新增 diff；把问题标成“一类 bug”，让作者一次修掉所有同类实例；已经发过的 finding 不重复发。夜间还会让审查 Agent 扫现有代码，把老问题在别处爆发之前找出来。

改完之后，内部 PR 的数据是：一轮审查加修复后即通过的比例从 65% 升到 78%；需要五轮及以上的从 8.9% 降到 1.5%；平均通过所需审查轮次从 2.08 降到 1.32。

**笔记补充**：这其实是在给审查设预算。无限轮次的边际收益递减，而边际成本对 Agent 作者更高——人可以把一个 nit 挥手放过，Agent 会照做，于是多一个 commit、多一轮审查。原文把“轮次到通过”和召回率一起跟踪，说明他们不只看“抓到了多少”，也看“抓到它花了多少轮”。

## 人还留在哪些位置

**作者观点**：把人从例行错误里撤出来，不等于人退出。团队仍然负责人工判断的五件事：

- 决定要不要做：方向、品味、范围。原文提到，即便在宣布审查瓶颈已解决之后，来自团队外部的改动仍保留人工审查，因为总得有人问“我们到底该不该做这个”。
- 审查高风险代码：计费、自动更新器、CI workflow。
- 审查会被别人照抄的架构。
- 读证据：测试输出、跑了什么命令、返回了什么、截图、审查者的 finding。如果说不清这些检查会漏什么，就该要求一次真正的审查，而不是快速点通过。
- 对结果负责：不管代码是谁敲的，每个上线的变更都有一个责任人。

“你合并，你负责”之所以没有变成互相甩锅，原文给了几个前提：变更足够小，容易读、调试和回滚；一切可逆，开关、revert 和分阶段发布能在几分钟内撤销大部分错误；爆炸半径决定审查规格，贵的代码自动获得更多人和更多检查；回归能通过遥测和内部使用快速浮现；以及它不被当成追责——拥有修复权意味着你掌握最多上下文，事故复盘看的是系统。

至于审查的第二项功能——让团队共享代码理解——原文说没有正式流程，也没人需要在脑子里装下整个 Claude Code。想看某一块时，就请 Claude 针对那一块写一份解释，几分钟就能得到与当前代码一致的说明；有人还会让它做一个小型可视化。读一行文案 diff 几乎学不到东西，读一个你即将修改的模块的解释则收获很大。

## 适用条件与边界

这套流程不是“装上 AI 审查就完事”，它依赖一串前提：PR 要小；新行为要能放在开关后面；要有可用的测试、构建和截图；要有遥测与值班；要有可信作者名单；还要愿意把事故和回滚变成每日运行的评测集。

反过来，如果变更不可逆、没有测试、没有监控、diff 常年几千行，或者贡献者大多不熟悉仓库，那么“零人工合并”的阈值就不该照搬。原文的产品本身也只发布 finding，不代替人批准 PR；Claude Code 自家仓库走得更远，是因为它同时具备上面那些条件。

成本也在原文里：建 CI、写 `CLAUDE.md` 和 `REVIEW.md`、维护评测集、调分类器、做 A/B 测试，都要投入。团队的目标写得很克制——大多数 PR 最多一个人经手（可以是作者），同时回滚率和事故率不上升。这不是“用机器换掉人”，而是“用机器换来人不用看的地方”。

## 理解检验

**1. 原文说六月到九月合并量增至两倍以上、回滚份额下降四成以上。能否据此推出“回滚次数减少了”？**

单凭这些变化无法判断。回滚次数等于合并量乘以回滚率。总量增加时，回滚率必须降到足够低，绝对次数才会下降。

**2. 既然“变更定级而不是作者定级”，为什么还要“可信作者名单”？**

两者管的是不同维度。变更定级回答“这个 diff 本身有多危险”，避免因为作者资深就放松；可信名单回答“这个人是否长期在这个仓库里、是否值得走轻路径”，是额外的信任门槛。所以低风险变更遇到名单外的作者，仍然要第二个人。

**3. AI 审查已经并行找 bug、投票、按严重度排序，为什么还要保留人工审批？**

因为审查能识别的是“可描述的缺陷”，不能替代对方向、架构、不可逆风险和责任归属的判断。原文把人工放在“要不要做、风险代码、架构、读证据、拥有结果”上，并且明确规定 Agent 的批准不算人类名额。零人工只在低风险、可信作者、自动化全绿这个窄条件下成立。
