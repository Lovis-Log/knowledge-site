## 核心问题：你在做的其实是管理

如果你整天和一个编码 Agent 待在一起，你已经在管理了。你反复选任务、写指令、委派、跟进、评估结果、决定什么能上线——这些动作合起来就是管理。Addy Osmani 的观察是：把 Agent 用得好的人，未必是最会写 prompt 的人，而是那些学会了管理的人，不管他们有没有意识到。

这个说法容易引起抵触。很多工程师选 IC 路线，就是想离工作近一点；他们见过朋友变成管理者，然后消失在日历里。作者先做了澄清：他不是劝你转成那种管理者，也不是说 Agent 可以替代管理者或同事。他说的“管理”是一个很窄的定义——**通过让别人把工作做好，来产生好结果**。

他给了一个很实用的切口：你对坏管理者的每一条抱怨，都可以当成与 Agent 交互的 bug report。比如烂 handoff：要求含糊、缺少上下文、期望反复变。IC 在接收端待了多年，往往知道一个好的 handoff 长什么样——这正是可以和 Agent 复用的经验。

原文的章节大致按影响力排序，越靠前越是高杠杆习惯。以下按这个顺序讲，并在最后单列一个**笔记补充**的委派案例，把散落的动作串起来。

## 给 Agent 一个能判断“做完了”的办法

**原文建议**：给 Agent 一种验证自己工作的机制，比如测试套件、构建或截图，并让它把结果拿出来作为证据。**反模式**是把“看起来做完了”当成确认——那等于你成了 Agent 的测试套件。

这个类比的起点是经理。你问一个有经验的经理，怎么在不读完所有东西的情况下确信团队在做对的事，他会讲护栏：CI、代码审查、看板、值班。没有护栏的新手经理会自己验证一切，一个季度内就成了瓶颈。Agent 的版本更直白：模型会在“工作看起来完成”时停下来；如果没有验证机制，“看起来完成”就是它唯一能获得的验证。

验证机制几乎可以是任何东西，只要它给出明确的通过/失败：测试、构建退出码、linter、diff 脚本、截图。作者引用的实践指南甚至说，跑这些验证的那条命令，是 `CLAUDE.md` 里最有价值的一行。

有了机制，可以用四种方式把它接进工作流：

- **直接要求**：例如“改完跑 auth 测试，一直跑到通过”。
- **设目标**：`/goal` 会让另一个模型在每个回合后做条件检查，适合长时间后台工作。
- **强制**：Stop hook 可以卡住回合，直到类型检查通过。
- **交给别人审**：`/code-review` 把 diff 发给一个没看过你对话的新子 Agent，就像作者不批准自己的 PR。

审查的范围也要指定。你让它“找问题”，它总能找到点什么；你让它只找正确性问题、忽略风格，它就会照做。作者说，好的经理要反馈时也是这么做的。

**笔记补充**：这一节真正解决的是“验证的所有权”。如果验证依赖你逐次肉眼确认，Agent 的产量越高，你越像瓶颈；如果验证是 Agent 自己能跑的命令，它就能进入“做—跑—看到失败—自己改”的循环。工具链里的 skills、hooks、子 Agent、MCP，本质上都在收紧这个循环，让你的注意力只花在 Agent 验证不了的地方。

## 交代它读不到的那部分上下文

**原文建议**：给 Agent 一份清晰摘要，说明它无法通过读仓库知道的东西：任务目标、为什么重要、约束、范围外的事项、成功标准。**反模式**是只丢一行任务、真正期望留在你脑子里；或者反过来，把 Agent 自己读代码就能发现的东西塞满 brief。

好的经理会把想要的结果、约束和目标讲清楚，但把“怎么做”留给执行的人。军队把这叫 commander's intent，Netflix 把它叫“context, not control”。

困难在于，你很难判断 Agent 缺的是哪块上下文。编码 Agent 每个任务的第一步就是读代码；当前模型从目录结构、约定、测试设置里提取信息的速度，远快于你手写描述。所以作者的建议是：写之前先想“它能自己读到什么”。如果代码里能读到、而且它真的会去读，就不用说。话要花在仓库里没有的部分——一次会议决定、某人部署的内部流程、这件事为什么重要、这一次“完成”具体指什么。

他给了一个把模糊任务改写成 brief 的例子（原文说数字只是示例）：

```text
把 /team dashboard 在 1 万人以上组织下的 p95 加载时间做到 2 秒以内。

为什么：企业管理员每天打开它，加载慢是他们的头号支持工单。

约束：不改 schema；保持 API 响应结构。

范围外：UI 改动；整页缓存。

验收：跑 scripts/perf/team.sh，给出改动前后的数字。
```

不是每个任务都要这么写。探索性工作完全可以先给一个泛 prompt，边做边细化。如果你还没准备好写 prompt，可以让 Agent 反过来面试你，直到它能写出规格；把规格存成文件，再开一个新会话从规格开始建。这份规格之后还能拿来对照审查。

另外，Agent 可能需要别的工具：issue tracker、错误看板、团队聊天。像对待新入职的同事一样对待它。像 `gh` 这种它已经知道的 CLI，通常不用额外说明。

## 让每一次纠错留下痕迹

**原文建议**：同一件事纠正超过一次，就写进团队的 `CLAUDE.md`，或者做成共享 skill；过一段时间再检查，新模型是否已经不需要这些纠正。**反模式**是每个 session 都手动纠一遍，或者依赖只存在你自己机器上的默契知识。

作者观察到，把 `CLAUDE.md` 用得好的团队会比较频繁地更新它，把“值得防止的错误”记下来。有的团队甚至在代码审查里 @claude，把一次反馈变成长期政策。

关键是简短。他列了四类应该写进去的东西：

- 怎么验证，给出精确命令；
- 代码里容易误导人的区域；
- 仓库里不存在的决定；
- 任何你已经纠正过两次的事。

**笔记补充**：这四类的共同点是“从经验里来、但不写下来就会丢”。文字之所以有复利，是因为它能跨越人员流动和模型更替；但也因此容易膨胀，所以作者反复强调 concise——一份过长的规则文件会把真正重要的约束稀释掉。

## 默认让它决定，只强制不能弯的部分

**原文建议**：默认让 Agent 自己决定，只对少数“必须总是”或“永远不要”的事使用硬强制，比如 hooks、deny rules。**反模式**是把规则写成全大写、给可选偏好设 hook，或者在新模型早已不需要时继续保留旧习惯。

作者引用 Andy Grove 的“任务相关成熟度”：监督程度应该取决于这个人在这个具体任务上的历史表现，而不是他的总体能力。还有一条给新经理的老建议：给人比你自己舒服程度多一点的回旋余地，同时在背后支持他、让他承担结果。

Claude Code 把这套东西显式化了：prompts、`CLAUDE.md`、skills 是**请求**，模型可以考虑、也可以选择不听；hooks、deny rules、managed settings 是**要求**，总是执行。大多数情况下，你希望 Agent 自己判断，因为看着真实代码的模型，往往比你提前写好的规则更清楚某条 guideline 是否适用。硬强制留给真正的硬需求，比如“永远不要改生成的客户端代码”“总是跑 license header 脚本”。

作者说这套建议是双向的：如果你在 `CLAUDE.md` 某一行上不断加码，Agent 还是不照做，那它应该变成 hook；如果一个 hook 表达的其实是偏好而不是要求，那就该删掉，让 Agent 自己决定。这像团队决定退休一个不再有用的流程。换了新模型也要调整：可以停止的习惯包括全大写指令、“think harder”（现在 effort 是一个设置）、“don't be lazy”。在当前模型上，这些往往导致过度强制的规则和过度工作。用 Agent 时，**过度流程就是新的微观管理**。

## 先计划，再开工

**原文建议**：在 Agent 开始写代码前先商定计划，读计划里的隐含假设，把任务切成互不重叠的并行工作。**反模式**是让多个 Agent 同时做重叠任务，然后花一下午处理合并冲突和重复决策。

好的工作流是先进入 plan mode，把计划迭代到对，再委派编码。计划足够好时，模型常常一遍就能建完。更大的任务可以开第二个 session，像 staff engineer 那样把计划读一遍——这是一次设计评审，也是抓错方向最便宜的地方。读计划时要找隐含假设；用作者的话说，在一对一里这就是问“你对什么不确定”。

任务分解本身也在被委派。`/batch` 会把一个大的机械改动拆成 5 到 30 个任务，展示计划，在各自独立的 worktree（仓库的独立检出）里执行，并为每个任务开一个 PR。你不再需要自己切分，只需要检查切片是否重叠，并确保共享接口先落地。否则会出现“虚假并行”：五个 Agent 做重叠任务，不会带来五倍产出，只会带来一个由五个作者共同制造的合并冲突。

## 早纠偏，快重启

**原文建议**：看它最开始那一分钟，发现偏航就纠。如果你已经做了两次失败的纠正，就开一个新 session，用更好的 prompt 重来。**反模式**是继续做第三、第四次纠正——你该纠正的是请求，不是 Agent。

有经验的经理知道：一个能干的人如果多次失手，问题可能在上游的指令、上下文或范围。Agent 版本更明确：一偏就按 Esc。两次纠正失败后，清掉 session，把学到的东西写进新 prompt。第三次纠正大多只是给模型更多要反复阅读和处理的信息，包括那些失败的尝试。

便宜的撤销也在改变游戏规则。`/rewind` 会把代码和对话回滚到早先的点，让“先试一个更激进的方案”变得低风险。好经理对员工也这样：如果撤销错误很便宜，就让人试；事后再复盘，把修复泛化进 `CLAUDE.md`。

**笔记补充**：这条建议有一个前提——失败的原因是请求写得不好。如果失败来自权限、环境、外部服务或需求本身变化，重启只会重复撞墙；这时该改的是环境或需求，不是 prompt。

## 委派任务，不委派判断

**原文建议**：Agent 做工作，你决定重要的事——产品取舍、安全边界、什么上线。把每个 diff 都当成“你会因为它被 on-call 叫醒”。**反模式**是看到测试绿了、命名合理，就批准一个大 diff；那不是代码审查，是“代码追认”。

没有经理能说“是我的下属发的，不是我”。作者承认自己也掉进过这个陷阱：他让 Agent 研究竞品差距，并写本地 PR 来补这些差距。他读了研究、扫了代码，差点就把改动推出去——那些改动给用户增加了复杂度，收益却很小。他委派了工作，也差点把决定一起委派了。这个陷阱很好踩：600 行的 diff，命名看着合理，测试是绿的，批准吧。

他给了一个分工建议：让 Agent 做风格、lint、审查跟进、常见 bug 和单元测试；让人做安全边界、合规和产品决策。

协调也一样。Agent 可以跟踪 handoff，但在相互竞争的请求之间做取舍、让人真的承诺，仍然是人的工作。

你不需要在每次变更的内循环里。你需要拥有的是外循环：约束是什么、你实际读多少输出、保留什么证据、什么必须由人签字。变更要小，因为**审查的单位就是理解的单位**。

## 设计一个不需要你在场的运行

**原文建议**：在部署一个自主任务之前，定义完成标准、自验证、边界、护栏和人工批准。**反模式**是睡前启动一个长流程，没有完成定义也没有停止点，第二天早上发现模型整夜在一个错误前提上工作。

跳过层级的管理者不管个体工程师的具体工作，他们管目标、护栏、检查点和负责人。Agent 也在走类似的轨迹：它们已经在把任务分给子 Agent，能按计划、CI 失败或新 PR 触发自主运行。前沿是自治理系统——能自主启动、自验证，只在需要决策时叫人。

角色的转变是从“控制这个 session”到“设计你的循环”。设计一次无人值守运行时，要问的五个问题和好经理在把项目交给高级工程师、自己去度假前问的一样：

- 它知道“完成”长什么样吗？（目标条件、规格文件，或一个必须变绿的失败测试。）
- 它有自验证机制吗？（测试套件、Stop hook，或审查步骤。）
- 它的边界在哪？（权限控制、沙箱、worktree，或只允许推的那一个分支。）
- 它的护栏是什么？（回合上限或花费上限。）
- 它在哪里产出，谁批准？（一个 PR 或总结；任何不可逆动作都要人批。）

作者还补了两个经理会认得的习惯：先 pilot，让批处理跑三个文件，改 prompt，再跑剩下的；任何新东西先看前几次运行，再放手——相当于试用期。

## 扩大验证，而不是扩大注意力

**原文建议**：只有当检查、目标和新的审查者能接手“盯着”的工作时，才按同样速度扩大 Agent 的使用；同时衡量质量，不只衡量吞吐。**反模式**是开超过你能审好的 session，用“AI 写了多少代码”衡量成功。

经理很快会知道自己的管理幅度：超过一定数量的直接下属，每个人分到的关注就变少，质量下降。Agent 也一样。作者把它叫**编排税**：超过前几个 Agent 之后，每多一个，需要的注意力比上一个更多。他多数日子跑四五个后台 Agent 加几个本地 session，有些天已经太多。

管很多 session 不是靠超级专注，而是把大部分监控交给自评、目标和全新上下文的审查者，把注意力留给决策。用通知代替轮询、用一个集中视图看后台任务，也有帮助。结论很硬：**你不能靠“监控更多”来扩展 Agent 数量，只能靠“需要监控更少”。**

然后要衡量系统，而不是活动。有用的指标包括 PR 的周期时间、新员工的 ramp up 时间、回滚或返工的频率。AI 代码占比不是一个有用的目标，因为你要的是质量和可靠性。格鲁夫的“配对指标”原则在这里适用：如果你测合并了多少 PR，就同时测回滚和返工。

## 决定不做什么

**原文建议**：问谁需要它、怎么知道它有效、什么会让你停，并限制在制品数量。**反模式**是把每个看似合理的想法都扔进一个 PR——反正构建很便宜；最后你得到一个团队必须审查、保护、支持和维护的杂物抽屉。

经理最重要的一个词常常是“不”。有了 Agent，“不”变得更难：开始工作几乎免费，午饭前就能把任何想法变成 PR。但审查和验证现在是稀缺资源。

作者说，那些老的管理问题反而更重要了：谁提出的？怎么衡量成功？什么时候该停？当构建很便宜，难的问题不是“我们能不能”，而是“我们该不该”。

## 【笔记补充】一个可复用的委派案例

以下场景是为本稿编的，不属于原文；它把前文的动作串成一次完整的委派。

假设一个内部团队仪表盘在大组织中加载过慢。任务是优化一个查询，把代表性数据下的第 95 百分位（p95）加载时间降到 2 秒内，同时保持数据结构和 API 响应兼容。

| 步骤 | 具体做法 | 对应前文 |
| --- | --- | --- |
| 1. 写 brief | 目标 p95、为什么要做、不能改 schema、范围外是整页缓存、验收命令是 `scripts/perf/team.sh` | 交代它读不到的上下文 |
| 2. 先要计划 | 让它列出要改的文件、是否动 API 形状、怎么回滚，先审一遍假设 | 先计划，再开工 |
| 3. 第一次运行 | 第一分钟检查它是否找到了查询和对应的 schema；要求贴出验收命令的前后数字 | 给一个能判断“做完”的办法 |
| 4. 两次纠正失败 | 开新 session，把失败原因和“不要改 API 形状”写进新 brief | 早纠偏，快重启 |
| 5. 同一纠正第二次 | 加一条类型或 lint 约束，或写进 `CLAUDE.md` | 让纠错复利 |
| 6. 人工只看三件事 | 查询是否保留权限过滤、结果是否等价、是否批准上线 | 委派任务，不委派判断 |
| 7. 事后 | 把验收命令和踩坑写进团队 skill，下次同类任务直接复用 | 设计不需要你在场的运行 |

这个案例里，Agent 负责实现和自查；人负责“要不要做、边界在哪、证据是否可信、是否上线”。如果把它改成“让 Agent 自己决定要不要改 API”，那就是把判断也委派出去了——也正是作者警告的那一步。

## 管理类比在哪里失效

**作者观点**：这个类比有用，但不完美。最常做这件事的人清楚它哪里不成立：

- **管人更难，技能不会反向迁移。** 能跑五个 Agent，不等于能管五个人。动机、冲突、职业发展、数月才能建立的信任，没有对应物。
- **返工几乎免费。** 你可以让 Agent 做你绝不会让人做的事。白板上的技术争论，Agent 可以直接建两三个方案让你比较。
- **Agent 没有经验，只有一本笔记本。** auto memory 只在一台机器上记录，不会转到同事的 session；它不是你职业生涯里积累的判断，所以那些教训要替整个团队写下来。
- **Agent 急切且自信。** 让一个好工程师做错事，他会反驳；Agent 更可能照做，你也更容易过度信任它。作者引用 Wharton 关于“认知投降”的研究：在该研究所用任务中，参与者多数时候接受了错误的 AI 答案，自信程度也上升。对策之一是让 Agent 反驳自己的答案。
- **你只有一种 Agent 原型，而且每几个月变一次。** 人类团队技能多样；你的 Agent 强弱一致，且随模型发布而变。
- **你仍然要培养初级工程师。** 当 Agent 接管了初级用来练基本功的活，经理要有意创造这些练习机会。
- **人的团队仍然重要。** 有时候你管了一天 Agent，没意识到挤掉了建设团队所需要的时间。

## 你不需要那个头衔

**作者观点**：好的 staff engineer 一直是这样工作的：写设计文档、设定上下文、做彻底的审查、让周围的人变好。Agent 让所有工程师第一天就能做这些，相当于给你一门管理速成课：反馈以分钟计而不是以季度计，你可以撤销自己的错误。工作正在从“写代码”变成“成为好代码被写出来的原因”。

没有人天生会管理，都是练出来的；Agent 让练习变便宜。他最后给了六条可执行的建议：

- 每个任务都要有一个它能跑的检查，并要它拿出证据。
- 告诉它看不到的，省略它能看到的。
- 写代码前先把计划过一遍。
- 同一件事纠正两次，就记进 `CLAUDE.md`；重复的流程做成 skill。
- 两次纠正失败，就重启并重写 prompt。
- 像“会因此被 on-call 叫醒”那样审 diff。

你不必想当管理者。但用好 Agent 的工程师，大概率会在这条路上学会管理。

## 理解检验

**1. 作者说“给 Agent 一个验证机制”，为什么这比“让它更努力”更有效？**

因为模型在“工作看起来完成”时就停。没有验证，“看起来完成”是它唯一能获得的信号；有了可运行的检查，它能自己进入“做—跑—看到失败—修正”的循环，不必由你充当测试套件。这也把注意力从逐次确认转移到只有人能判断的部分。

**2. “委派任务，不委派判断”具体分的是什么？作者自己的反例说明什么？**

分的是执行与决策：Agent 可以做实现、风格、lint、常见 bug、单测；人保留产品取舍、安全边界、合规和上线决定。作者让 Agent 研究竞品并写 PR，读了研究和代码后差点推出去——那批改动会增加用户复杂度，收益却很小。他委派了工作，也差点把“该不该做”一起委派。这说明大 diff、绿测试和合理命名都不能替代判断。

**3. 为什么作者说“不能靠监控更多来扩展 Agent，只能靠需要监控更少”？**

因为注意力有管理幅度：超过几个 Agent 后，每多一个带来的边际注意力成本高于上一个（编排税）。可行的扩展方式是把监控交给自评、目标条件和新上下文审查者，人只处理决策和异常；同时用 PR 周期、返工率等系统指标衡量，而不是用 AI 代码占比。
