## 这一篇在讲什么

用 AI 做一个漂亮的静态网站已经不难，难的是把它变成一个真正的应用：登录、支付、数据库、实时更新、视频通话、消息系统，还要让这些部分彼此配合。

演示项目是一个**健身教练平台**：用户可以找教练、购买训练计划、看视频课、聊天、预约一对一课程；教练有自己的后台，管理客户、上传课程、查看收入。平台抽取佣金。

技术选型是作者的示范，不是通用推荐：

| 部分 | 工具 | 用途 |
| --- | --- | --- |
| 框架 | Next.js | 全栈应用 |
| 后端 | Neon | Postgres、认证、存储、函数、实时 |
| 实时聊天与视频 | Stream | 消息、回复、话题、输入状态、一对一视频 |
| 媒体 | ImageKit | 视频上传、图片优化、自适应码率播放器 |
| 支付 | Stripe | 一次性购买与平台抽成 |
| 可观测性 | Sentry | 错误监控、会话回放、AI 自动排查 |
| 托管 | Cloudways Velocity | 部署与自动重新部署 |

作者反复强调：**这套课真正重要的不是这个应用，而是流程**。先规划、再做界面、然后一个功能一个功能实现，每完成一个就人工检查、让 AI 复核、提交，再进入下一个。

## 工作流：一个闭环

作者把它画成一个循环，值得先记住整体形状：

1. **规划**：说清楚要做什么、有哪些页面、用户流程、技术栈。不知道自己在建什么，AI 只能靠猜。
2. **界面**：根据规划做 UI，给 AI 参考图，而不是让它自由发挥。
3. **逐个功能实现**：一次只做一个功能。
4. **人工自检**：自己点一遍，确认功能真的能用。
5. **AI 复核代码**：让 AI 检查实现是否有问题。
6. **修复 → 提交**：功能完成就保存进度；没完成就重复上面几步。
7. 还有功能就回到第 3 步，没有了就结束。

这个循环里，第 4 步和第 5 步的顺序很关键：**先自己确认功能对不对，再让 AI 看代码**。否则 AI 可能在错误的目标上做优化。

## 第 1 步：环境与部署

### 先把最小项目跑起来

安装 Node.js 和 VS Code 后，新建空文件夹拖进编辑器。AI 工具可以用 Claude Code、Codex、Cursor 等，命令各不相同，但流程一致。作者建议至少订阅 20 美元档，理由是用量足够跟完整套流程。

先用一句最简单的话验证工具链是通的：

```text
build me a nextjs project, keep it simple, a habit tracker application
```

这个习惯记录器不是最终项目，只是为了确认「AI 能建项目、能跑起来」。

```bash
npm run dev
```

打开本地地址，新增一条习惯、刷新页面确认数据还在，工具链就验证完了。

### 尽早部署，并接上自动部署

作者在写任何业务代码之前就先部署，这一步的价值常被低估：**从第一天起就有一个真实可访问的地址**，后面每加一个功能都能立刻在线上看到。

做法是：在 GitHub 新建仓库并推送代码（可以直接让 AI 执行你粘贴的 git 命令），然后在 Cloudways Velocity 里连接 GitHub、选中仓库、点部署。平台会自动识别这是 Next.js 项目，一两分钟就能得到一个临时域名。

更关键的是自动部署：平台监听仓库的新 commit，**任何一次推送都会触发重新部署**。于是日常开发变成：

```text
给项目加一个明暗主题切换，然后提交并推送到我的仓库。
```

AI 改代码、提交、推送；平台自动重新部署；线上地址几分钟后就更新了。你不需要进任何控制台。

## 第 2 步：规划——让 AI 采访你

新手最常见的错误，是打开编辑器就说「我要做 X，请帮我做」。作者说，从第一天起不可能想到所有细节，但有一个办法可以让细节自己浮现：**plan mode + 一个「采访我」的提示词**。

提示词的核心是告诉 AI：

> 你的任务是对我即将描述的项目做访谈。就每一个细节、每一个决策向我提问，不要自己猜功能。

作者举的例子很具体：涉及支付时，AI 会问用 Stripe 还是一次性付款、要不要订阅、月费定 20 还是 50。这样一轮下来，可能产生 20–30 个问题。

描述项目时，把技术栈也一起说清楚：

```text
我想用 Next.js 做一个全栈健身教练平台。
用户可以找教练、购买训练计划、看视频课、和教练聊天、预约一对一课程。
教练有自己的后台，管理客户、查看训练计划和收入。
技术栈：Neon 做 Postgres、认证和实时；Stripe 做支付；
Stream 做带 reaction、回复、话题的聊天和一对一视频；
Sentry 做错误监控和自动调试；
Cloudways 做托管与部署；ImageKit 做图片视频上传、优化和播放器。
界面要现代、有质感。
```

### 回答问题时的取舍

拿到问题后，作者提醒了一个很容易被忽略的细节：**不要无脑全选「推荐选项」**。教程里为了节省时间可以全选默认，但在真正要变现的项目里，有些问题的不同选项会显著改变产品形态和成本，必须逐条读。

回答完会生成一份计划，界面会展示出来。此时同样要通读，不满意就改成你的版本，再接受。

最后把计划落成文件：

```text
把这份计划保存到 PLAN.md 文件里。
```

### PLAN.md 与 AGENTS.md 的分工

- `PLAN.md`：这个项目要做什么、架构决策、技术栈、假设。
- `AGENTS.md`：给 AI 的项目规则，类似 README 但对象是 AI 而不是人。里面可以写「必须用这个技术栈、绝不用那个」「每次改动都提交 commit」等。

`AGENTS.md` 的特殊之处是：**即使你不主动引用它，它也会一直加载进上下文**。所以它适合放那些「每次都必须遵守」的约束。

## 第 3 步：界面——用参考，而不是凭空生成

直接说「给我做一个好看的 UI」，得到的通常是随机风格。作者的做法固定为三步：

1. 新建 `design/` 文件夹；
2. 去 Pinterest 搜 `website design`，再叠加领域词（如 `fitness website design`），挑一张真正喜欢的截图存进去；
3. 把图片附给 AI，并说明这是灵感来源。

指令大致是：

```text
分析 PLAN.md，然后为整个应用搭建完整的 UI 设计。
现在用假数据，不要接认证、数据库或支付，只做界面和硬编码数据。
界面风格参考我附上的这张图。
```

这里有两个值得学的细节：

- **先做完整 UI，后接真实数据。** 界面阶段只用假数据，可以快速看到整体效果；等界面定稿，再把假数据换成真数据。作者在后面的后端章节正是这样做的。
- **背景图这类素材单独生成。** 把参考图截图发给 GPT 或 Gemini，要求「生成这张背景图，不要文字和 logo」；也可以用 Higgsfield 这类付费工具并通过 MCP 直接在编辑器里出图，省去来回切换。

生成的界面里，有些交互是假的（比如预约时段点不动），这是故意的。把「哪里不对」截图给 AI，它会继续改，直到满意为止。

## 第 4 步：后端——Neon

界面完成后，开始把假数据换成真数据。Neon 提供 Postgres、认证、存储、函数、AI Gateway 和实时功能。

关键技巧不是「让 AI 写代码」，而是**让 AI 告诉你它需要什么**：

```text
这是我从 Neon 拿到的接入文档。先读 PLAN.md，然后实现认证，
并在数据库里创建一些真实数据。
如果需要在 Neon 控制台做什么，给我一份待办清单，我来做。
如果需要某些值，直接告诉我，我去取。
```

这个「给我待办清单」的模式贯穿全篇。第一次用某个控制台时，你不知道该复制哪个值、该点哪里；与其自己摸索，不如让 AI 列出它需要的东西，你照着做。

实践中的几个点：

- 数据库连接串、认证 URL 等放进 `.env.local`，注意去掉复制时带的引号。
- 认证用的是 Better Auth；上线前要把生产域名加进可信域名列表。
- **改环境变量之后必须重新部署**，否则线上仍然是旧值。
- 遇到不确定的事（比如「开发环境要不要加 localhost」），直接截图问 AI，而不是猜。

验证方式很实在：用 Google 登录一次，再用邮箱注册一次，去 Neon 的认证面板能看到新用户，就说明链路真的通了。

### 实时功能要用两个账号验证

预约功能做完后，作者开了第二个浏览器、登录另一个账号，两边并排放在一起：一边预约某个时段，另一边**不刷新**就应该看到该时段被禁用。

第一次没成功。处理方式不是读日志，而是**截图 + 描述 + 要求**：

```text
这是我每次预约时会看到的结果（附图）。
请修复它，并确保所有人都能实时收到更新。
```

修好后重新验证，实时更新生效。这是全篇最值得记住的排错方式之一：截图比文字描述准确得多。

## 第 5 步：实时通信——Stream 的 agent skills

聊天和视频通话如果从零搭，代价极高（信令、媒体服务器、扩展性）。Stream 提供现成的 SDK，而它的 **agent skills** 解决的是另一个问题：让 AI 知道怎么正确使用这套 SDK。

做法是：安装 Stream CLI，登录，在项目里初始化：

```bash
npm install -g @stream-io/stream-cli
stream login
stream init
```

初始化时会选择组织与应用，然后询问「为哪个工具安装 skills」。选你用的工具（Claude Code、Cursor、Codex 等），它就会把一整套文档作为 skill 写进项目。之后在编辑器里输入 `stream` 就能查询这些文档，例如「如何在 Node.js 里生成用户 token」。

**为什么这很重要？** 没有 skills，AI 只能凭训练数据里的旧版 SDK 猜 API；有了 skills，它读的是当前版本的官方文档。

集成指令要写清边界：

```text
把 Stream 的聊天和视频集成到我现有的 Next.js 应用里。
保留现有的认证后端和 UI 设计。
加入带频道、reaction、回复和话题的实时消息，以及带摄像头和麦克风控制的视频通话。
使用服务端安全生成 token，并遵循最新的官方 SDK 文档。
```

测试时逐项确认：摄像头开关、麦克风开关、加入通话、reaction、录屏、共享屏幕、结束通话。

聊天界面第一版很乱——按钮被遮住、话题打不开。作者同样用截图 + 一句「UI 彻底坏了，请修好，你可以用浏览器自己测，直到看起来正常」解决，并且提前连好了 Chrome MCP，让 AI 能自己打开页面验证。结果一次提示就修好了。

随后验证聊天功能：发消息、加 reaction、开话题、同时发到主聊天、附件、GIF 命令、编辑、删除、引用。确认无误后提交。

### 一次真实的部署失败

提交后线上部署失败。原因很清楚：**Stream 的 API key 和 secret 只加在了本地，没有加到托管平台的环境变量里**。加上、保存、重新部署，成功。

这类失败很典型：本地能跑 ≠ 线上能跑，环境变量是最常见的差异来源。

## 第 6 步：可观测性——Sentry 与自动修复

用户不会在出错时给你发邮件，他们会直接关掉页面、再也不回来。Sentry 的作用是当那个「瞭望塔」：捕获错误、记录会话、给出上下文。

作者列出的能力里，对本篇最重要的是三个：

1. **错误监控**：出错时间、影响范围、调用栈、请求与用户上下文。
2. **会话回放**：出错时录屏，能直接看到用户点了什么、在哪一步崩掉。
3. **AI 自动排查（Seir）**：读代码找根因，生成修复，并开一个 pull request 等你合并。

安装方式已经变成「让 agent 来做」：在 Sentry 控制台复制给 agent 的安装命令，在终端执行，再把生成的提示词贴给 AI。期间需要通过 MCP 完成 OAuth 授权——作者第一次也没成功，重新执行 `/mcp`、再授权一次就好了。

### 手动流程：分析 → 计划 → 修复 → PR

先故意制造一个错误，触发后进入 issue：

1. 点击分析，Seir 给出根因与复现步骤；
2. 让它制定计划；
3. 让它写修复代码；
4. 生成 pull request；
5. 你 review 并合并。

**一个容易踩的坑**：Seir 读的是 GitHub 上的代码，不是你本地的文件。所以修复前必须先把代码推上去，并且要在 Sentry 里配置好 GitHub 集成与仓库映射。

### 自动流程：错误达到阈值就自己修

配置好代码映射后，同一个错误触发超过一定次数（演示中约 10 次），Seir 会自动开始分析、修复并起草 PR。作者让 AI 故意把错误触发 15 次以上，然后去 GitHub 看，已经有现成的 PR；合并即可，整个过程人只需要 review。

合并后让本地同步：

```text
我刚刚合并了一个 pull request，请拉取最新代码。
```

### 日志与追踪

生产环境不要用 `console.log`。Sentry 的 structured logs 可以打标签、可查询、存在云端，并且和 trace、error、replay 关联。用户量小的时候感觉不到价值，但到几百、几千用户时，它就是排查问题的唯一入口。

## 第 7 步：媒体——ImageKit

ImageKit 负责图片和视频的上传、存储、变换与分发。

- **URL 即变换**：在图片 URL 里加参数就能裁剪、缩放、旋转、叠加，一次上传可以得到头像、页头、卡片三种尺寸。
- **自动优化**：自动压缩并输出 WebP/AVIF 等现代格式。
- **视频播放器**：支持自适应码率（按网速切清晰度）、字幕、章节和预览缩略图；课程视频可以设为私有，只有购买者能看。

集成同样靠一句「需要什么环境变量告诉我」：

```text
把 ImageKit 接入这个应用，覆盖 PLAN.md 里的第三、四阶段。
功能包括……（列出）
告诉我你需要哪些环境变量，以及哪些要加到 Cloudways。
```

ImageKit 文档每页都有「Copy for LLM」按钮，可以把整页说明直接贴给 AI，省去手工整理。

## 贯穿全程的几条方法

1. **先规划再动手。** 访谈式提示词把「AI 猜功能」变成「你回答问题」，这是整篇投入产出比最高的一步。
2. **给参考，而不是给形容词。** 「现代、有质感」几乎没有信息量；一张截图能立刻对齐审美。
3. **一次一个功能，做完就验证、就提交。** 每个功能都走「实现 → 人工自检 → AI 复核 → 修复 → 提交」。
4. **让 AI 告诉你要什么。** 控制台里该点哪里、该复制哪个值，直接问，让它给待办清单。
5. **截图是最高效的 bug 报告。** 报错界面、错位按钮、失败状态，截图加一句要求，通常比描述有效。
6. **本地能跑不等于线上能跑。** 环境变量、域名白名单、重新部署，是最常见的三类差异。
7. **尽早引入可观测性。** 有真实用户之后，看不见的错误比看得见的错误更贵。

## 理解检验

**1. 为什么作者建议「先人工自检，再让 AI 复核代码」，而不是反过来？**

参考答案：AI 复核的是代码实现层面的问题（结构、边界、潜在 bug），前提是「这段代码在做正确的事」。如果功能本身就不符合预期，先让 AI 看代码，它可能在一个错误的目标上优化，浪费一轮修改。先人工确认功能行为正确，再把「如何实现得更稳」交给 AI，两次检查各管一层，顺序不能颠倒。

**2. plan mode 的「采访式」提示词解决了什么问题？为什么它比直接描述需求更有效？**

参考答案：直接描述需求时，没被说到的细节会由 AI 自行猜测，最终成品常与预期不符。「采访我」把 AI 从执行者变成提问者，就支付方式、订阅价格、教练入驻方式等逐个决策向你确认，把隐含假设显式化。一次可能产生 20–30 个问题，覆盖的正是你原本没想到的部分。作者同时提醒：不能无脑选推荐项，重要项目要逐条读，因为不同选项会改变产品形态与成本。

**3. 为什么界面阶段要先只用假数据，等界面定稿后再接真实数据？**

参考答案：界面阶段的目标是快速看到整体效果、验证布局与交互，假数据能立刻铺满所有页面，不受后端进度影响。如果一开始就接真实数据和认证，任何一个后端问题都会阻塞界面迭代，反馈变慢。等界面定稿后再接真实数据，替换的是数据来源而不是重做界面，改动范围可控。作者在后端章节正是按这个顺序做的。

**4. Seir 自动修复前，为什么必须先配置 GitHub 集成与代码映射？**

参考答案：Seir 读的是 GitHub 仓库里的代码，不是你本地工作区的文件。没有 GitHub 集成，它拿不到源码；没有代码映射（project → repo → 分支），它不知道该去哪个仓库找对应文件。两者缺一，分析就会失败或改错地方。另外，修复前要先把本地改动推送到 GitHub，否则它基于旧代码生成 PR。

**5. 部署失败最常见的原因是什么？这篇里给出了哪两个具体例子？**

参考答案：最常见的是本地与线上环境不一致，尤其是环境变量。例子一：Stream 的 API key 与 secret 只写进了本地环境，托管平台没有，部署直接失败；补上并重新部署后成功。例子二：改完环境变量后必须触发一次新的部署，否则线上仍用旧值。除此之外，认证服务要求把生产域名加入可信域名列表，也是上线时才暴露的一类差异。

**6. Stream 的 agent skills 解决的是什么问题？没有它会怎样？**

参考答案：它把当前版本的官方 SDK 文档打包成 AI 可读的 skill 写进项目，让 agent 在写 Stream 代码时依据最新文档，而不是训练数据里的旧 API。没有它，AI 容易用过时或臆造的接口，出现「代码看起来合理但跑不通」的情况；有了它，可以直接问「如何在 Node.js 生成用户 token」并获得当前版本的答案，集成提示词里也就能要求「遵循最新官方 SDK 文档」。
