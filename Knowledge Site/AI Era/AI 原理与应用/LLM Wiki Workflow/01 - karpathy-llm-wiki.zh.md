## 主张

最近一段时间，Karpathy 发现自己很大一部分 token 消耗不再是「操作代码」，而是「操作知识」——以 Markdown 和图片的形式存储。原因是当前模型已经足够擅长做这件事。

具体做法是搭建个人知识库：**原始资料进 `raw/`，LLM 把它增量编译成一份 wiki，人在 Obsidian 里阅读与提问**。

有一个前提值得单独强调：wiki 由 LLM 写入与维护，人很少直接动它。这和「人写笔记、AI 帮忙润色」是相反的分工。

## 工作流的六个环节

### 1. 数据摄取

把文章、论文、仓库、数据集、图片等源文档索引进 `raw/` 目录；然后用 LLM 增量地「编译」出一份 wiki——本质是一个目录结构里的 `.md` 文件集合。

wiki 的内容包括：

- `raw/` 中所有数据的摘要
- 反向链接（backlinks）
- 按概念归类的文章，以及文章之间的互相链接

把网页文章转成 Markdown 用 Obsidian Web Clipper；再用一个快捷键把相关图片下载到本地，方便模型直接引用。

### 2. IDE

Obsidian 充当「前端」：同时查看原始数据、编译后的 wiki 和派生的可视化。作者提到试过一些插件以其他方式渲染与查看数据，例如用 Marp 做幻灯片。

### 3. 问答

当 wiki 足够大之后（他某个研究主题的 wiki 约有 100 篇文章、40 万字），就可以针对它提出各种复杂问题，让 agent 自己去查、去研究。

一个反直觉的结论：**不需要上复杂的 RAG**。在这个规模下，模型自己维护索引文件和每篇文档的简短摘要，已经能顺利读完相关材料。

### 4. 输出

不只给文本答案，而是渲染成 Markdown 文件、Marp 幻灯片或 matplotlib 图，再回到 Obsidian 里查看。不同问题可以有不同的可视化形式。

更关键的是：这些输出常常被「归档」回 wiki，用来增强后续查询。于是每次探索都会累积进知识库，而不是散落在聊天记录里。

### 5. 巡检（linting）

对 wiki 跑「健康检查」：

- 找出数据不一致的地方
- 借助网络搜索补全缺失数据
- 发现值得写成新文章的有趣关联

这一步是增量清理，目标是提升整体数据完整性。模型也很擅长提出「接下来该问什么」。

### 6. 额外工具

为处理数据而开发小工具，例如一个用 vibe coding 写出来的朴素搜索引擎：既能在网页界面里直接用，也常被当作 CLI 工具交给 LLM，用于更大的查询。

### 再往前一步

随着仓库变大，自然会想到合成数据生成与微调——让模型把数据「装进权重」，而不只是放在上下文窗口里。这是作者提到的后续探索方向，本文没有给出实现。

## 一句话总结

一定数量的源数据被收集起来，由 LLM 编译成 `.md` wiki，再由各种 CLI 在 wiki 上做问答与增量增强，全部在 Obsidian 里查看。人几乎不手写或编辑 wiki，那是 LLM 的领域。作者认为这里存在一个「了不起的新产品」的空间，而不该只是脚本的拼凑。

## 值得追问的地方

评论区提出了一个作者尚未回答的关键问题：**增量编译的粒度和批次**。

提问者说，如果一篇一篇处理，单篇上下文不足以判断该如何划分目录；他想知道是否存在最优批次大小，或者是否需要多阶段处理。作者只回应了「我也正想拍个视频讲这个」，没有给出答案。

这暴露了整套方法里最不透明的部分：wiki 的目录结构、概念文章的划分、摘要的详略，都依赖 LLM 的判断，而这些判断在不同批次规模下可能不一致。规模小时看不出来，wiki 长到几百篇后，结构漂移会变成维护成本。

另一个隐含前提是：**模型要能可靠地维护索引与摘要**。作者的体验是「在这个规模下够用」，但 40 万字是一个具体量级，超过之后是否仍成立，文中没有数据。

## 理解检验

**1. 为什么作者说「不需要复杂 RAG」？这个结论依赖什么前提？**

参考答案：因为在约 100 篇文章、40 万字的规模下，LLM 自己维护的索引文件与每篇文档的简短摘要，已经足以让它找到并读完相关材料，不需要额外的向量检索或分块管线。这个结论依赖两个前提：wiki 的规模仍处于「模型可以直接读相关文件」的量级；以及模型能稳定地维护索引与摘要。规模显著变大或索引质量下降时，结论不一定成立。

**2. 在这套工作流里，人和模型的分工与常见做法有什么不同？**

参考答案：常见做法是人写笔记、AI 辅助润色或检索；这里反过来——LLM 负责写入与维护全部 wiki 内容，人主要在 Obsidian 里阅读、提问和判断。人几乎不直接编辑 wiki。这种分工的好处是知识库能持续被增量编译与巡检，代价是人需要信任模型的分类与摘要，并且要能发现结构漂移。

**3. 为什么「把输出归档回 wiki」很重要？**

参考答案：因为它让每次探索都累积成知识资产。如果答案只留在对话里，下次还要重新查；归档后，后续查询可以直接复用，wiki 也会因为这些输出而变得更有用。这与「linting 发现新文章候选」形成同一个循环：使用越多，知识库越完整。

**4. 评论区提出的未解问题是什么？它为什么重要？**

参考答案：问题是增量编译的批次大小与阶段划分——逐篇处理时，单篇上下文不足以决定目录如何划分；是否存在最优批次或多阶段流程，作者没有回答。它重要是因为目录结构与概念划分直接决定 wiki 是否可用，而不同批次规模可能导致分类不一致，规模越大越难纠正。

## 与前后内容的关系

这篇给出的是一个「知识库由模型维护」的框架，和本库里把剪藏编译成站点笔记的流程是同一类工作：摄取 → 编译 → 问答 → 回写。区别在于这里的产物是给人读的 Markdown 站点，而 Karpathy 的产物是给模型自己查询的 wiki。若要把它落到工程上，Agent 如何组织上下文、如何压缩历史，可参考《AI Agent 工程》的「拆解 Codex 的 Agent 循环」一篇。
