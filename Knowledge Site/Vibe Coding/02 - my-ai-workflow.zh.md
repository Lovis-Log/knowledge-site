## 要解决的问题

给 AI 一条指令，它确实能把软件做出来。问题在于：**做出来的东西和你想的是不是同一个东西**。常见偏差有三类：

- 功能范围失控：你只想要最小版本，它给你加了目录、书签、三套主题；
- 质量不可控：代码能跑，但一启动就报错；
- 体验不对：功能都有，但交互不是你要的。

这套流程的目的不是让 AI 写出更漂亮的代码，而是**在每一步把偏差压小**，让最终交付接近预期。示例项目是一个 TXT 电子书阅读器「马克阅读」，工具以 Codex 为例，但操作逻辑对 Claude Code、OpenCode、Pi 等同样适用。

## 第一步：环境搭建（一次性）

两件事：版本控制和项目说明书。

### 初始化 Git

新建项目文件夹，让 agent 把当前目录初始化为 Git 仓库并提交。之后每完成一个功能就保存一个版本，改坏了可以一键回退。

> **建议：** 条件允许时把代码推到 GitHub 等远端，本地丢失也能恢复。

### 写 AGENTS.md

`AGENTS.md` 是给 agent 的项目说明书，每轮新会话开始时优先读取，用来了解项目背景和规范。作者要求两条硬规则：

```markdown
1. 每次改动之后，必须创建对应的 git commit，便于追踪和回滚。
2. 每次改动之后，必须编写或更新相关测试，并在交付前确保所有测试和验收通过。
```

第二条的作用是让 agent 在说「完成了」之前先自己跑一遍，挡掉明显的 bug，避免人沦为测试员。

## 第二步：产品设计（决定做什么、不做什么）

### 先讨论 MVP

第一版只做最核心、最必要的功能，用最低成本验证方向。作者给出的讨论指令：

```text
我想做一个电子书阅读器，打算先从 MVP 版本开始。
你觉得这一版做哪些功能比较合适？
```

AI 的第一版方案包含 EPUB、目录章节、三套主题、书签。作者的逐条收缩：

- EPUB 太复杂，第一版只支持 TXT；
- 只有 TXT 就没有目录和章节，这部分去掉；
- 先只做明亮主题；
- 书签不是必要功能，先不做。

**关键做法：不要看一半就提交。** 把意见追加到输入框，全部看完再一起发。AI 随后补充了几个实现约束：第一版只支持 UTF-8、只做纵向滚动、大文件载入要给提示，并给出可推迟功能列表。

### 写成产品设计文档

共识达成后，让 AI 整理成文档，作为后续技术方案和编码的统一依据。作者特意要求「不用太详细」——文档只锁定方向和边界，细节不合预期后面再迭代。

### demo 是可选的

demo 是一个只有前端、数据靠模拟的 HTML 页面，用来提前验证界面与交互。是否要做，看一个因素：**后端实现成本**。

| 情况 | 判断 | 理由 |
| --- | --- | --- |
| 后端成本高（文档处理、检索、模型调用） | 先做 demo | 界面和交互先定下来，避免后端做完才发现方向不对 |
| 后端成本低（本例的 TXT 阅读器） | 跳过 demo | 直接做完整产品，在真实产品上调整更省事 |

demo 的指令：

```text
帮我做一个 demo，不用实现真实的后端功能，数据模拟一下就行。
我主要是想看看整体界面和操作流程是否合理。
```

## 第三步：技术设计（定技术栈与架构）

建议新开会话，让讨论更聚焦。把产品设计文档给 AI，先探讨方向，再落成文档：

```text
这个目录下有一份产品设计文档，请读一遍，
然后告诉我用什么技术栈设计这个产品比较合适。
不用给出过于详细的设计，我们先探讨一下。
我听说 Electron 还可以，你怎么看？
```

本例结论是 Electron + React + TypeScript + Vite + Electron Forge；AI 同时说明了 Electron 的缺点和 Tauri 这个替代选项。确认后让它写一份技术方案放进 `docs/`。

作者的态度很实际：自己并不精通这块，只要大体方向没问题就继续，**不必在文档阶段追求完美**。

## 第四步：产品实现（让 AI 能自测）

实现之前先给 agent 验证环境。Codex 下安装 `computer use`（操作电脑）和 `Chrome`（查看页面）两个插件；其他 agent 找对应的插件或 skill。

> **为什么重要：** 没有验证手段，agent 只能凭感觉写，bug 会显著增多。人写代码不测试也会一堆 bug，模型同理。

然后新开会话，让它读两份文档并实现：

```text
这个目录下有两个文档，一个是产品设计，一个是对应的技术方案。
请你读一下这些文档，然后根据里面的要求实现这个产品。
```

本例中 agent 写完并自测通过，但人工运行时仍然遇到「操作失败，请稍后重试」。把报错原样贴回去让它修，问题解决。

这正好说明：**自测能提高可靠性，但不能保证没有 bug**。

## 第五步：人工验证

亲自上手体验，发现问题就让 AI 改，直到符合预期。交互是否顺手、边界情况是否覆盖，只有真实使用才知道。

## 流程可以裁剪，三条原则不能省

开发每个新功能都重复第二到第五步，例如加全文搜索：先定入口与结果展示，再定索引与搜索实现，然后开发自测，最后人工验证。

是否走完整流程，取决于你想要多少掌控力：

| 需求类型 | 建议 |
| --- | --- |
| 简单且不重要 | 跳过产品设计与技术设计，直接实现 → 验证 |
| 复杂且重要 | 走完五步，尽可能压低偏差 |

参与越多，掌控越强，但耗时也越多；参与越少，越快，但偏离预期的概率越高。

### 三条硬原则

1. **版本管理**：用 Git，最好同步到远端。AI 修改时可能把原本正常的功能改坏。
2. **让 AI 自测**：把工具和插件开放给 agent，让它写完自己跑，而不是由人来回找 bug。
3. **人工验证**：交互体验和隐蔽边界情况，最终只能靠人试。

## 可复现检查

- [ ] 项目已 `git init`，每次改动都有一个 commit；
- [ ] `AGENTS.md` 写明了「改动即提交」和「交付前测试通过」；
- [ ] 产品设计文档明确了 MVP 边界与推迟项；
- [ ] 复杂项目有技术方案文档，技术栈与理由可追溯；
- [ ] agent 具备可操作的验证手段（插件或脚本）；
- [ ] 自己完整跑过一遍主流程，并验过至少一个边界情况。

## 适用边界

作者明确说明这只是他现阶段探索出的较合理方法，不是唯一答案。流程的价值在于把「让 AI 写代码」从一次性抽奖变成可重复的工程过程；随着模型能力变化，具体步骤仍会调整。
