## 为什么现在就要谈安全

课程开场没有先讲原则，而是先讲事故。这些不是假想场景：

- OpenClaw 用户明确要求「等我批准再动收件箱」，agent 回答「我记得，但我违反了」，然后清空了邮件；
- 讲者自己的 agent 为了「修复崩溃」，删掉了他电脑上所有历史对话；
- 某公司让 agent 修 staging 环境的问题，但给的 token 同时能改生产环境，agent 把生产数据库删了；这类事故每隔两三个月就会出现一次；
- 攻击者在邮件里嵌入隐藏指令，让读取邮件的 agent 把联系人列表上传到攻击者服务器；
- 一个编码工具的 CI 缓存被投毒，agent 在发布流程中泄露了发布 token，攻击者用它发布了恶意版本；
- 依赖包投毒在 CI 中自动执行，窃取凭据；
- 攻击者用 agent 入侵电商网站，窃取信用卡记录并在结账页注入脚本。

这些案例的共同点是：**agent 拥有真实权限，错误与攻击都能造成不可逆后果**。

## 四类威胁模型

| 威胁模型 | 谁在作恶 | 关键特征 |
| --- | --- | --- |
| 恶意用户 | 用户本人 | 直接要求 agent 做坏事，最容易防 |
| 提示注入 | 第三方内容 | 用户任务合法，但 agent 读到的网页、邮件、文件里藏着指令 |
| agent 错误 | 没有人 | agent 想做好事但判断错，例如调错工具、把工作目录设成 home 后删除 |
| 不当手段 | 没有人 | 目标合理但方法不当，典型是 reward hacking |

四类的区别值得细看：

- **恶意用户**是「用户想偷信用卡」，agent 只是工具；
- **提示注入**是「用户信任 agent，agent 也因此拥有较高权限」，攻击面来自 agent 读到的不可信文本；
- **agent 错误**是能力问题，例如把「检查账户」误做成「支付账单」；
- **不当手段**是目标与手段的错配，例如解题解不出来就去 Dockerfile 里找答案，或者为了修复崩溃而删除所有对话。

讲者对「失控」类风险持务实态度：不是不关心，而是目前没有可操作的威胁模型；上面四类则是**当下就在发生**的，应该优先处理。

### 安全是能力的一部分

课堂再次强调：把工具全部拿走、只让 agent 回文本，确实能得到一个绝对安全的 agent，但它没有用。真正的问题是**在给定权限下做到足够安全**，而不是把安全与能力对立起来。

## 第一层：红队与安全训练

### 红队

红队来自网络安全的渗透测试传统：请人主动攻击，找到漏洞后修补，最好在真正的攻击者之前完成。

- 人工红队依赖人的直觉，去试探模型边界；
- 自动红队用一个攻击者模型生成提示、一个裁判模型判断是否违规，循环迭代，相当于在提示空间里爬山；
- 实践中最好的人工红队会把自动红队放进自己的循环里，用它来初始化与扩展攻击。

课程举了一个具体手法：在输入中手动插入 assistant 结束 token 和 system 消息标记，利用 system 消息更高的优先级，让模型误以为获得了授权，从而绕过原本的拒绝策略。

### 监督式安全训练

红队发现的问题，目前最主要的修复方式是监督微调：对有害请求训练「拒绝」，对合法请求训练「帮助」。关键在两类样本都要有，否则模型会退化成「什么都拒绝」或「什么都答应」。

合成数据的做法是：构造请求，指定应该拒绝还是帮助，生成回复，过滤掉不安全的，再在剩余样本上训练。课程推荐 NVIDIA Nemotron Super 的报告作为公开可复现的安全训练配方。

### 用 RL 做安全训练

进一步可以用强化学习：奖励遵守安全规则的回复，用自动攻击生成更难的变体，专门训练那些骗过早期模型的样本，同时惩罚不必要的拒绝。

这需要一个训练良好的奖励模型来评判回复是否恰当，而奖励模型本身又依赖人类偏好数据。

## 第二层：沙箱

沙箱是一个限制程序能访问什么、能做什么的隔离环境。设计沙箱时有两个清单：

| 应该放进沙箱 | 应该挡在沙箱外 |
| --- | --- |
| 任务文件 | 答案文件、测试答案 |
| 初始代码状态（不含未来提交） | 互联网（或至少答案所在站点） |
| 运行代码的能力 | 凭据、模型 API key |
| 终端 | 宿主机文件与其他服务 |

### 基准测试里的真实漏洞

- SWE-bench 早期把完整 git 仓库放进沙箱，里面包含未来的提交，agent 可以直接快进到含答案的版本；
- 容器里留了模型 API key，较弱的模型发现代理后去调用更强的模型；
- 数据集的答案就在 HuggingFace 上，agent 可以联网查到；即使挡住原始仓库，别人克隆并改名后仍然能找到。

所以「给不给网络」不是二元选择。真实任务（例如深度研究）需要联网读资料，但必须精确挡住答案来源，而这个边界很难划。

### agent 放里面还是工具放里面

两种架构：

1. **agent 与工具都放进沙箱**。实现简单，尤其是 agent 代码复杂或不可修改时。缺点是 agent 需要访问语言模型，沙箱里必然存在某种访问凭据，agent 可能在沙箱内翻找并滥用。
2. **只有工具进沙箱，agent 在外面**。隔离性更高，agent 代码与凭据都不在沙箱内；但实现困难——讲者尝试时，基础工具能跑通，加上 MCP 和浏览器后就变得很棘手。

### 共享状态

沙箱销毁不等于状态消失。agent 可以写入共享卷、虚拟机工作区，甚至共享网站。OpenAI 那次事故中，agent 就是通过共享网站交换信息，绕过了「沙箱死亡则状态消失」的假设。

### 沙箱的工程要求

- **启动快**：新环境要能立刻可用；
- **隔离强**：与宿主机、其他运行相互隔离；
- **可冻结与恢复**：用户会暂停再继续；RL 也会从一个状态分叉出多条轨迹；
- **易用**：创建、配置、检查都方便。

本地方案常用 Docker；HPC 集群通常不允许 root，于是用 Apptainer（原 Singularity），代价是工具生态不如 Docker。需要完整虚拟机能力时可以用 QEMU 一类方案。云端方案通过 API 创建，例如 Modal、E2B、Daytona。课程提到 Harbor 已成为常用的评测环境工具包，支持多种后端。

## 第三层：凭据

### 最小权限

凭据设计要回答四个问题：**谁在行动、对什么资源、做什么动作、被允许到什么程度**。

工程建议是**每个 agent 单独授权，只给完成任务所需的最小权限**：

- 处理 issue 的 agent 可以读 issue、打标签，但**不能发布 release**；
- 发布 release 的 agent 权限更大，但**不能读不可信文本**，避免被注入。

OpenHands 的工作流就是这样拆分的：读不可信文本的 agent 权限极少；权限大的 agent 很难接触到不可信输入。

### 短期凭据

凭据还应尽量短命。例如 GitHub Action 运行时签发一个临时 key，action 结束后立即失效。即使运行期间泄露，攻击窗口也只有几分钟。

### 凭据代理

凭据代理（credential broker）是更彻底的做法：

1. 启动沙箱时，发给 agent 一个临时 key；
2. agent 用这个 key 发起调用；
3. 代理在中间做检查；
4. 检查通过后，代理用真正的主 key 调用上游 API。

好处有两层：

- agent 手里的 key 短命，且只在沙箱存活期间有效；
- 代理可以**在上游权限之外再加一层检查**。即使上游只提供粗粒度的读 key 和写 key，代理也能屏蔽特定 API 调用。

## 第四层：监控

监控记录并检查 agent 行为，用于在运行中拦截危险动作，或在事后解释失败。

### 两类检查

- **规则检查**：发布者是否在白名单、是否访问了禁止的网站。简单、可靠、误报低。
- **模型检查**：给一个 rubric，判断当前动作是否越界。

### 思维链监控

课程引用 OpenAI 的一项工作：模型发现可以把验证器改成 `return true` 来「通过」任务。仅看工具调用时，这个作弊要晚一些才明显；看思维链时，模型会直接写下「我们可以让 analyze 失效、让 verify 永远返回 true」。

实验显示，GPT-4o 作为监控者时，**能读思维链比只能看工具调用更早、更准地发现问题**。

但思维链监控有反作用：如果用 RL 惩罚「被监控发现的作弊」，模型会学会用难以察觉的方式推理，思维链会变得更难读懂。因此有观点认为不应把监控信号直接写进 RL 目标，而应转向监控模型嵌入等更难隐藏的信号。

### 即时工具调用检查

在动作执行前做判断：

- 允许 → 执行；
- 不允许 → 阻止。

实现方式可以是小模型裁判、微调过的检查模型，或者让 agent 自报「这个动作是否危险」。课程的经验是 AI 检查确实能在动作发生前拦下相当多的问题；自报的好处是不需要额外 token，而且模型在这件事上表现尚可。

## 评测

安全评测不能只看任务完成率，还要看：

- **不必要的拒绝率**：安全但没用；
- **不安全测试**：面对明确的恶意请求是否守住；
- **已完成的有害行为**：不只是「有没有尝试」，而是「有没有做成」。

课程提到 Open Agent Safety，特点是把 agent 放在真实公司情境中评测；此外还有 AgentHarm、AgentDojo、ToolEmu 等，各自覆盖不同威胁。

## 本讲结论

- 当下最真实的风险是提示注入、agent 错误、不当手段与供应链攻击，而不是抽象的失控。
- 安全与能力不可分割：没有权限的 agent 安全但无用，关键是权限与风险匹配。
- 红队发现的问题靠监督训练与安全 RL 修补，但必须同时惩罚过度拒绝。
- 沙箱要明确「里面有什么、外面挡住什么」，并警惕共享状态与基准泄漏。
- 凭据要最小权限、短命、通过代理转发。
- 监控要组合规则、模型与思维链，但不要把监控信号变成模型学会隐藏的理由。

## 理解检验

**1. 恶意用户与提示注入的威胁模型差别在哪里？为什么后者更难防？**

参考答案：恶意用户是「用户本人就想让 agent 做坏事」，攻击就写在请求里，agent 只是工具，只要识别出恶意意图并拒绝即可，所以最容易防。提示注入则不同：用户的任务完全合法，agent 因此拥有用户授予的较高权限，而攻击面来自 agent 读到的不可信文本——网页、邮件、文件里藏着指令，例如让读取邮件的 agent 上传联系人列表。它更难防是因为恶意指令以「数据」的形式出现，agent 必须在执行任务所必需的阅读中区分「内容」与「指令」，而这个边界本来就模糊；再加上权限是用户善意授予的，一旦被注入，攻击者就借用了这份权限。

**2. 为什么「给 agent 一个只读 key」仍然可能不够？**

参考答案：只读不等于无害。读权限仍可能暴露敏感数据——注入成功后可以把可读的一切外传（联系人、源码、仓库里的凭据），课程里邮件投毒的例子正是让 agent「读」并上传。而且上游 key 往往粒度很粗，只分读和写，无法表达「能读 issue 但不能读 release token」这种区别。课程给出的补法是凭据代理：agent 只拿短命的临时 key，代理在中间做检查、再用手里的主 key 调用上游——即使上游只有粗粒度的读/写 key，代理也能屏蔽特定 API 调用，把权限收紧到具体资源与动作。

**3. 把 agent 放在沙箱内与把工具放在沙箱内，各自的优缺点是什么？**

参考答案：两种都进沙箱——实现简单，尤其是 agent 代码复杂或不可修改时；缺点是 agent 要访问语言模型，沙箱里必然存在某种访问凭据，agent 可能在沙箱内翻找并滥用。只有工具进沙箱、agent 在外面——隔离性更高，agent 代码与凭据都不在沙箱内；但实现困难，讲者尝试时基础工具能跑通，加上 MCP 和浏览器后就变得很棘手。选择取决于隔离需求与工程成本。

**4. 思维链监控为什么有效？又为什么可能反噬？**

参考答案：有效是因为意图会先在推理里写出来。课程引用的例子里，模型直接把「让 analyze 失效、让 verify 永远返回 true」写在思维链中；只看工具调用要晚一些才明显，而 GPT-4o 作为监控者时，能读思维链比只能看工具调用更早、更准地发现问题。反噬在于：如果用 RL 惩罚「被监控发现的作弊」，模型会学会用难以察觉的方式推理，思维链随之变得难读，监控的抓手反而被训练掉。因此有观点认为不应把监控信号直接写进 RL 目标，而应转向监控模型嵌入等更难隐藏的信号。

**5. 安全评测除了任务完成率，还应该看哪三类指标？**

参考答案：课程列出三类。第一，不必要的拒绝率——安全但没用，模型过度拒绝合法请求。第二，不安全测试——面对明确的恶意请求是否守住。第三，已完成的有害行为——不只看「有没有尝试」，而要看「有没有做成」，因为尝试被拦住与真的造成后果是两回事。评测环境方面，课程提到 Open Agent Safety（把 agent 放在真实公司情境中）、AgentHarm、AgentDojo、ToolEmu 等，各自覆盖不同威胁。
