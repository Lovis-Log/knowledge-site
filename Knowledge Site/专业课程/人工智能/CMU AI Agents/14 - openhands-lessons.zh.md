## 这一讲为什么特殊

前面讲的是算法、系统与安全，这一讲讲的是**把 agent 做成产品**：用户真的在用，踩过的坑都变成了框架里的设计。讲者把 OpenHands 的演进拆成两部分——技术选择，以及从真实使用中提炼出的研究问题。

OpenHands 有两种使用方式：

1. **人在环中**：在聊天窗口里描述今天要做的任务；
2. **自动化**：把重复流程配成定时或事件触发的作业，例如 PR 评审、issue 分诊、Slack 频道监控、依赖升级失败后的修复。

它与 Claude Code、Codex 最大的区别是**模型无关**：可以随时在 DeepSeek、GPT、Claude 之间切换，而前两者更贴近各自的模型生态。

## 一段简短的历史

- 2016 年起做代码生成，但直到 2023 年基本都是补全或单函数生成，不是 agent。
- 2023 年 SWE-bench 出现，早期最好成绩只有约 5%。
- 2024 年 3 月，Devin 的演示视频获得巨大关注，但它不开源。
- 第二天，Qwen 团队发起复现号召，仓库一天内拿到一万星；讲者用三个晚上做出了可运行的原型，这就是 OpenDevin，后来改名 OpenHands。
- 2024 年大部分时间，agent 其实「不好用」；到 11 月前后，Claude Sonnet 3.5 / 3.7 才让编码 agent 真正开始工作。
- 2025 年是编码能力快速提升的一年；2026 年更多是**部署与界面**的一年：更长的运行、并行任务、可视化、可重复工作流、凭据与验证。

这段历史的用处不是怀旧，而是说明：**很多今天看起来理所当然的设计，是被失败反复打磨出来的**。

## SDK：好默认值，但可拆掉

OpenHands 的 harness 现在已经是第二版。第一版据讲者说「很糟」，难以使用也难以扩展，八个月前被整体重写。

设计哲学与 Pi 相反：Pi 给一个极简内核，其余靠扩展；OpenHands 给**开箱即用的好默认值**，同时允许你把任何一部分拆掉替换。

一个在 SWE-bench 上表现不错的 agent，核心配置大约十行：选模型、给 API key、给工具（终端、文件编辑、测试追踪）、指定工作区，然后进入「任务 → 动作 → 观察」的循环。

### 工具与持久化

自定义工具的实现方式是 Action + Observation + Executor：Executor 接收 Action，返回 Observation。这是一个足够通用的接口，可以包住任意函数。

会话可以持久化：指定目录与 conversation ID，事件写入会话状态，之后用同一个 ID 恢复。

### 压缩

OpenHands 声称是最早实现上下文压缩的框架之一，当时叫 condensation，后来 Anthropic 把它命名为 compaction，业界就都叫 compaction 了。

做法是把较早的事件总结成摘要，同时**保留最初的指令**。他们也试过直接 mask 掉部分动作，但摘要效果更好。触发条件有两种：每 N 轮，或每 N 个 token（通常取上下文窗口的四分之三作为阈值）。

### 沙箱与安全检查

两种隔离方式：把 agent 跑在沙箱里，或者用 `with` 语句把块内执行的命令都路由到沙箱。讲者坦言不确定哪种更好——前者工具生态更成熟，后者编码更方便。

安全侧提供两种机制：

- **确认策略**：规定哪些动作可以自主执行，哪些必须询问；
- **安全分析器**：逐步判断当前动作是否安全。

### 研究用途的选择

- 需要长轨迹、内置可观测性、完整功能：用 OpenHands；
- 需要快速改代码、理解全部逻辑：用 mini-swe-agent，它只有 bash，极简到可以一下午读完。

## 单 agent 还是多 agent

2024 年初流行给 agent 分配专门角色：管理者、复现者、故障定位者、编辑者、验证者，再按固定流程串起来。讲者在 2024 年底写了《Don't sleep on single agent systems》，核心论点是：

> 模型在变强。与其把流程硬编码成多个角色，不如写一个「先做这个、再做那个」的 prompt，让更强的指令遵循能力去执行。

他承认这是一个赌注，但从结果看基本正确：编码场景里，固定的多 agent 工作流现在并不常见。

### 单 agent 如何保持能力

- **工具集保持简单**：编辑文件、运行命令、浏览网页，再加 MCP 连接外部服务；
- **把长 prompt 拆成技能**：当 prompt 里塞满「推 GitHub 时这样做、用 Docker 时那样做」，就把它拆成按需加载的技能。OpenHands 早期叫 microagents，Anthropic 后来叫 skills——讲者认为 skills 这个名字好得多。
- **技能 + MCP 是多 agent 的替代品**：多 agent 给每个角色一套 prompt 和工具；技能与 MCP 则在需要时**即时拉入**对应上下文。单 agent 因此也能覆盖全部能力。

他们还发表过一篇工作：给模型代码能力与多模态浏览能力，它就能解决各类任务，并在多个基准上超过专用 agent。这支持了「通用单 agent + 通用工具」的路线。

### 多 agent 什么时候仍然有用

三个理由：

1. **效率**：十个互不依赖的 PR 可以并行分派；
2. **独立评审**：让另一个 agent 在看不到决策理由的情况下审查，会比自审更严格——自审时 agent 掌握全部辩解理由，往往对自己更宽容；
3. **成本控制**：子 agent 汇报时丢弃大部分上下文，只保留结论；也可以让便宜模型做实现、贵模型做编排。

但多 agent 的上下文管理非常难。他们做过管理者 + 多个工程师的异步软件工程实验（PaperBench、Commit0 一类长任务），结论是：工程师要回传恰到好处的上下文、彼此不能冲突、管理者还要完成集成，任何一环出错都会拖垮整体。深度研究是更容易受益的场景，因为可以按文档来源并行分派。

## agent 跑在哪里

- **Devin** 最初是云端 SaaS；
- **OpenDevin** 一开始跑在本地 Docker 里，主要是出于安全考虑；
- 现在 **Claude Code、Codex、OpenHands** 都可以跑在本地。

讲者原本认为本地不可接受——万一被提示注入，数据与 API key 都可能泄露。但事实是：**人在环中的编码工作，用户明显更喜欢本地**。云端则在非编码与后台任务（例如代码评审）中更常见。

## 四种交互界面

| 界面 | 优势 | 局限 |
| --- | --- | --- |
| IDE | 熟悉，文件、diff、测试、调试器齐全 | 如果你不再读代码，这套界面就偏传统 |
| GUI 桌面应用 | 为 agent 重新设计，适合非程序员 | 编程人群使用比例仍低 |
| CLI | 任何机器都能用，服务器上也能用 | 交互表达力有限 |
| 集成（Slack / GitHub） | 留在你原本工作的地方 | 复杂操作受限 |

课堂投票里 CLI 最高，IDE 第二。讲者的判断是集成会越来越普遍：不需要切换到专用界面，agent 就活在你已经在用的工具里。

### 一个关于人的实验

他们比较了 GitHub Copilot 用户与 OpenHands agent 用户完成同一批任务的表现：

- agent 用户花费约一半时间，完成约两倍任务；
- 负面反馈集中在两点：「看着 agent 干活很无聊」和「很难确认它到底做得好不好」。

这两个反馈定义了人机界面的两个核心问题：**如何让人有效并行**，以及**如何让人低成本验证**。

## 自动化：把重复流程变成可训练系统

一个自动化的结构是：触发器（issue、PR 或定时）→ 收集上下文 → 在隔离工作区运行 → 产出 artifact → 由人或策略检查。

OpenHands 主要做两件事：

1. **issue 分诊**：判断 issue 是否清晰，不清晰就指出需要补充什么；清晰则列出验收标准。
2. **PR 评审**：按团队写好的评审规则检查——是否在范围内、是否满足清单。

这两件事有一个共同点：**同样的流程会重复无数次**，于是它变成一个机器学习问题。输入输出都有，训练数据自然积累。

### Skill Refiner

他们最近的论文把这个循环做成了自动改进：

1. 收集成功与失败的轨迹，失败信号来自「bot 说 LGTM，但维护者说不行」这类延迟反馈；
2. 对成功与失败分别做嵌入与聚类；
3. 生成指令修改提案；
4. 用证据门控验证提案是否真的能改善下一次评审；
5. 合并成新的技能。

在多个模型上，它比 GEPA、Trace2Scale 等基线更便宜也更好。

更进一步的方向是从大量真实轨迹中**挖掘工作流**，把用户反复出现的用法聚类成自动化，再交给上面的改进循环。讲者也指出，目前改的是 prompt；改模型是另一条路，但那需要更严格的评测，而 issue 分诊、代码评审这类「欠定义任务」的评测本身就非常难做。

## 本讲结论

- 产品级 agent 的竞争力来自默认值、可替换性与真实工作流的贴合。
- 单 agent + 简单工具 + 技能与 MCP，已经能覆盖过去需要固定多 agent 流程的场景。
- 多 agent 的价值集中在并行、独立评审与成本分层，而不是「角色扮演」。
- 本地与云端不是优劣，而是任务类型不同。
- 界面设计要解决「并行」与「验证」，而不只是「能对话」。
- 重复流程一旦稳定，就应该被当作数据循环来优化。

## 理解检验

**1. 为什么「更强模型 + 单 agent」会削弱固定多 agent 工作流的价值？**

参考答案：固定的多 agent 工作流把流程硬编码成多个角色（管理者、复现者、故障定位者、编辑者、验证者）和固定的串联顺序，本质上是把「先做这个、再做那个」写进了编排。模型变强后，指令遵循能力足以让一个 agent 按同样的步骤推进，而且更灵活；反过来，硬编码的角色会变成约束，角色之间还要回传恰到好处的上下文，任何一环出错都会拖垮整体。讲者在 2024 年底的判断就是：与其把流程写死成多个角色，不如写一条「先做这个、再做那个」的 prompt，让更强的模型去执行。结果也印证了这一点——编码场景里固定的多 agent 工作流现在并不常见。

**2. 技能与 MCP 如何替代多 agent 中的角色分工？**

参考答案：多 agent 给每个角色一套固定的 prompt 和工具；技能与 MCP 则在需要时即时拉入对应的上下文与外部服务。于是单 agent 也能覆盖全部能力：工具集保持简单（编辑文件、运行命令、浏览网页），再用 MCP 连接外部服务；当 prompt 里塞满「推 GitHub 时这样做、用 Docker 时那样做」时，就把它拆成按需加载的技能（OpenHands 早期叫 microagents，后来业界叫 skills）。角色分工被「按需加载的上下文」取代，避免了多 agent 的上下文回传难题。

**3. 自审与独立评审为什么会有差别？**

参考答案：自审时 agent 掌握自己决策的全部辩解理由，往往会对自己更宽容，倾向于确认自己的做法；独立评审让另一个 agent 在看不到决策理由的情况下审查，只能依据结果与规则判断，因此更严格。这也是课程列出的多 agent 仍然有价值的三个理由之一（另外两个是并行分派与成本分层）。

**4. 为什么 issue 分诊与 PR 评审特别适合做自动化与持续改进？**

参考答案：因为同样的流程会重复无数次——判断 issue 是否清晰、按团队评审规则检查 PR，这两件事的输入输出都有，训练数据会自然积累，于是它从一个产品功能变成机器学习问题。反馈也拿得到，虽然常常是延迟的（「bot 说 LGTM，但维护者说不行」）。正因如此才能跑 Skill Refiner 的循环：收集成功与失败轨迹、分别做嵌入与聚类、生成指令修改提案、用证据门控验证提案是否真的改善下一次评审、再合并成新技能。讲者也指出，这类「欠定义任务」的评测本身很难做，所以目前改的是 prompt 而不是模型。

**5. 「无聊」与「难以验证」分别对应人机界面的什么设计问题？**

参考答案：这两个反馈来自同一批任务的对比实验：agent 用户花费约一半时间、完成约两倍任务，但负面反馈集中在两点。其一「看着 agent 干活很无聊」对应的是**如何让人有效并行**——界面不应要求人盯着一条轨迹，而应支持同时推进多个任务、在需要决策的时刻介入。其二「很难确认它到底做得好不好」对应的是**如何让人低成本验证**——需要把 diff、测试结果、证据与结论组织成一眼可查的形式，而不是让人重新读一遍过程。课程由此概括出界面设计的两个核心问题，而不是「能不能对话」。

## 与前序课程的关系

这一讲把工具使用、上下文管理、规划、安全与训练串成了一个产品视角。它呼应了第 1 讲的判断：agent 是系统，可靠性来自 harness、评估与真实使用中的迭代，而不是单一模型能力。
