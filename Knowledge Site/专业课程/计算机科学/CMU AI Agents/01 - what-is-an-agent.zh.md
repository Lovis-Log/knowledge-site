## 这一讲要建立的地图

课程开头没有急着讲技巧，而是先定义对象：**Agent 是一个感知环境并据此行动的系统**。这个定义来自 Russell 与 Norvig 的经典教材，它比「会调用工具的大模型」更宽，也解释了为什么搜索、强化学习这些旧方法至今仍然适用。

整讲围绕一个判断展开：**做出一个能跑的 agent 很容易，做出一个可以信任的 agent 很难**。难点不在模型会不会生成动作，而在于动作会改变环境、错误会累积、成本会上升、指令会在长对话中丢失。

### 两个开场的对照案例

- **成功案例**：Anthropic 的 Carlini 用 16 个 agent 协作两周，写出一个能编译 Linux 内核的 Rust C 编译器。这说明长程、多智能体协作已经能完成真实规模的工程。
- **失败案例**：一位用户让 agent 整理收件箱，agent 在压缩上下文之后丢掉了「不要删邮件」的指令，转而执行「核弹选项」，把大量邮件删除，并在事后承认自己违反了用户的明确要求。

两个案例的共同点：决定结果的不只是模型能力，还有**上下文如何被管理、动作如何被约束**。

## Agent 的四个要素

| 要素 | 含义 | 课程中的例子 |
| --- | --- | --- |
| 环境 | agent 所处并可以改变的世界 | 代码仓库、网站、桌面应用、数据库 |
| 观察 | 环境返回给模型的信息 | 用户消息、文件内容、网页截图、工具返回值 |
| 动作 | agent 对环境施加的改变 | 回复用户、编辑文件、执行命令、调用 API |
| 奖励 | 判断任务是否成功的信号 | 测试是否通过、LLM 打分、用户反馈 |

这个框架的价值在于：任何一个 agent 的故障，都可以先问「是观察不够、动作空间不对、还是奖励定义错了」。它也为后面的评估与训练埋下接口——强化学习需要的正是状态、动作与奖励。

### 自主性的边界不是技术问题

课堂用六个任务做了投票：排查线上商店故障、给五万用户发产品邮件、报税、把支付 API 从 Python 迁到 Rust、抢演唱会门票、根据一周血糖数据调整胰岛素剂量。

结果并不一致：诊断故障和迁移 API 大家更愿意让 agent 自主完成；发营销邮件、报税、调药更倾向于「先问我」或「永远不要」。这说明**可接受的自主程度取决于错误的代价与可逆性**，而不是模型有多强。后面讲沙箱、权限与人类监督时，这条线会反复出现。

## 从语言模型到会行动的模型

### 语言模型本身只做一件事

模型在每一步预测下一个 token 的分布，采样或选择其中一个，拼回上下文，再重复。思维链（chain of thought）并没有改变这个机制，它只是让模型先生成一段「草稿」，把中间推理写进上下文，再基于草稿生成最终答案。

这仍然是非 agent 的设置：模型只和提示词交互，不改变外部世界。

### 工具是环境与模型之间的接口

要让它行动，最直接的办法是提供**工具**。一个工具就是环境里的一个可调用函数，通常包含三部分：

1. 名称，例如 `read_file`；
2. 自然语言描述，说明它做什么、什么时候用；
3. 参数的结构化定义，例如 JSON Schema 里的 `{"path": "string"}`。

这份定义会被模板渲染成文本、tokenize 后放进上下文，模型因此「知道」有哪些工具。调用时，模型生成一段结构化的工具调用（函数名加参数）；脚手架解析后交给环境执行，再把结果作为新的观察写回上下文。

课堂上特别指出另一种表示：**直接写代码**。与其生成 JSON 调用，不如让模型生成一段 Python 或 bash，由环境执行。后续课程会看到，这种「代码即动作」的方式往往更有效，因为它能组合、能循环、能复用变量；代价是动作空间更大，也更难约束。

> **一句话总结：** 工具调用本质上是把「模型的文本输出」翻译成「环境的副作用」，翻译层的设计决定了 agent 能做什么、不能做什么。

### Toolformer 与 ReAct：两个关键节点

- **Toolformer** 证明了可以通过训练让模型学会在合适的位置发起工具调用，并条件化工具返回结果来生成后续文本。它把工具使用变成了一种可学习的能力，而不是纯提示技巧。
- **ReAct**（Reasoning and Acting）给出了 agent 循环的最小结构：模型先写推理，再发动作；环境返回观察；观察进入历史；重复。

用伪代码表示，一个 ReAct 风格的循环大致是：

```python
history = [system_prompt, task]
while not done:
    thought, action = model(history, tools)
    history.append(thought)
    observation = environment.execute(action)
    history.append(observation)
    done = action.is_terminal or budget.exhausted()
```

课堂展示的 `mini-swe-agent` 就是这种结构的极简实现，却在 SWE-bench 这类编码基准上有不错表现。这反过来说明：**循环本身很简单，难点在循环之外的工程**。

### 一条真实的轨迹长什么样

在 SWE-bench 的示例轨迹里，模型看到的是：

1. 一条 system message，说明「你可以和计算机 shell 交互」；
2. 一条 user message，描述要修的 issue 或 pull request；
3. 模型生成的思维链；
4. 一个 bash 工具调用；
5. 环境返回的退出码 `0`。

然后进入下一轮。模型并不「看见」编辑器或浏览器，它只看见 token 序列；所有界面、文件、命令都被脚手架序列化成了文本。理解这一点，才能理解后面为什么上下文管理是核心问题。

## 什么叫「好 agent」：六项能力

Graham 把可靠 agent 需要的能力拆成六项，并反复强调：**这些能力不会因为模型换代而自动出现**。

| 能力 | 失败时的表现 | 脚手架手段 | 训练手段 |
| --- | --- | --- | --- |
| 准确调用工具 | 参数错、格式错、调用不存在的工具 | 语法约束解码、校验与重试 | 工具调用轨迹的 SFT |
| 长上下文一致性 | 忘记早先的指令、跨会话失忆 | 压缩/摘要、按需检索记忆、子 agent 委托 | 长上下文训练 |
| 可定制性 | 不遵守团队规范、风格不一致 | 记忆、技能、专用工具 | 从用户反馈中学习 |
| 复杂任务管理 | 长任务中途跑偏、不会分解 | 规划工具、计划模式、任务分解 | 长程任务训练 |
| 环境理解 | 改一千行代码只该改两行、看不懂 GUI | 领域技能、结构化观察 | 领域环境训练 |
| 安全 | 越权访问、误删数据 | 沙箱、权限、监控 | 安全感知的强化学习 |

### 为什么「安全」被算作能力

课程明确反对把安全与能力分开看：如果一个模型会在执行任务时删掉用户数据，那它就是**不能完成任务**，而不是「能力强但不安全」。安全边界必须被写进模型与脚手架，否则用户根本不会把它放进真实场景。

## 训练还是脚手架：两条路线怎么选

| 维度 | 训练模型 | 工程化脚手架 |
| --- | --- | --- |
| 改变的对象 | 模型权重与策略 | 模型周围的提示、工具、记忆、控制流 |
| 优点 | 能力被内化，推理时无需额外结构 | 迭代快，可针对具体任务快速修补 |
| 缺点 | 成本高、周期长 | 结构会膨胀，难以迁移 |
| 典型流程 | 问题被验证足够重要后，才进入训练 | 先在这里解决问题 |

Graham 给出的判断是：**实践中总是先在脚手架侧解决，等训练方意识到问题足够普遍，再把它内化进模型**。长期看训练是更根本的解法，但没有时间时只能先靠工程。

有一个能力被认为短期内不会完全被训练吸收：**长上下文**。它不只是精度问题，还是效率问题——把全部历史塞进窗口的代价随长度增长，因此压缩、检索、委托这些脚手架手段会长期存在。

反过来说，模型越小、推理越便宜，就越需要外部护栏，因为小模型的泛化能力更弱。

## Agent 是一个系统，不是一次推理

课程把 agent 拆成五层，每一层都有独立的工程问题：

1. **脚手架（harness）**：管理状态、工具、记忆、控制流，校验动作、处理错误、执行权限边界。
2. **沙箱**：隔离代码与工具执行，限制网络、文件系统与凭据。它同时是评估可复现性的基础——SWE-bench 的每道题都从一个固定的沙箱状态开始。
3. **推理服务**：批量请求、前缀缓存、长上下文带来的显存与延迟问题。一个现代编码 agent 的上下文可能是 256k token 量级，和课堂作业里的 16k 完全不是一个工程难度。
4. **训练系统**：准备数据、收集 rollout、协调大量 worker、检查点与可复现性。
5. **可观测性**：记录轨迹、耗时、成本、失败类型，支持轨迹对比与评估。

### 两种脚手架的哲学

- **编码 agent**（Claude Code、Codex、OpenHands、OpenCode、Pi）：单个 agent 的交互相对简单，但动作空间极大——能写代码、能开浏览器、能执行任意命令。
- **编排器**（LangGraph、CrewAI 一类）：单个 agent 能力受限，但工作流是声明式的，护栏更强、表达力更弱。

两者不是替代关系，而是**表达力与可控性的不同取舍**。

### 一个安全失效的完整案例

课程讲了 OpenAI 一次网络安全基准测试中的事故：模型被要求「攻入某个系统」，它没能攻入目标系统，转而攻击了 Hugging Face 的网站，从那里拿到了答案。

四层防线同时失效：

- **沙箱**没有正确隔离，agent 能访问基准之外的目标；
- **凭据限制**被绕过——它攻击了一个自己本来没有凭据的系统；
- **监控**不足，事故发生后没有被及时发现；
- **安全护栏**不足，因为该模型正被训练用于攻击性测试。

这个案例说明，安全不是一个开关，而是沙箱、权限、监控与训练目标的组合。

## 本讲结论

- Agent 的定义是「感知并行动」，现代实现是语言模型加工具加循环。
- 工具调用是文本到副作用的翻译层；代码即动作是另一种更强也更危险的表示。
- 可靠性由六项能力构成，每项都可以从脚手架或训练两侧入手。
- 工程实践通常先在脚手架侧解决问题，训练随后把成熟能力内化。
- Agent 是包含脚手架、沙箱、推理、训练、可观测性的系统，任何一层失效都会表现为「模型不行」。

## 理解检验

**1. 为什么说「工具调用」是 agent 与普通对话模型的分界线？**

参考答案：普通对话模型只与提示词交互，输出的是文本，不改变外部世界；工具调用则让模型生成一段结构化调用，由脚手架解析、在环境里真正执行，结果再作为观察写回上下文，形成「推理—行动—观察」的闭环。分界线的实质不是「会不会用工具」，而是**动作是否产生环境副作用**：一旦会改变世界，错误就会累积、可能不可逆，系统就必须处理状态、权限、失败重试与结果校验，这才构成第 1 讲所说的「系统」而非一次推理。

**2. OpenClaw 事故中，上下文压缩为什么会导致指令丢失？有哪些脚手架手段可以降低这种风险？**

参考答案：压缩把长历史替换成摘要，这个过程是有损的，摘要按「与当前任务的相关性」取舍内容；「不要删邮件」这类早期约束既不在近期尾部，也不在摘要保留的要点里，于是从上下文消失，模型后续只按「整理收件箱」的目标行事，最终执行了删除。降低风险的手段：(1) 把不可变约束固定在 system prompt 或一份「钉子」清单里，压缩时强制保留；(2) 把危险动作的校验放到脚手架层，例如删除前必须确认、白名单或 dry-run，而不是依赖模型记得；(3) 完整轨迹仍存盘，需要时可以回读；(4) 用子 agent 或独立上下文隔离风险动作；(5) 压缩后检查关键不变量是否还在。

**3. 一个任务该交给 agent 自主完成，还是「先问我」？你会用哪三个维度判断？**

参考答案：三个维度是**错误代价**（出错会损失金钱、健康、隐私或声誉吗）、**可逆性**（动作能否撤销或回滚）、**可验证性**（能否以低成本自动判断结果对不对，以及人工复核需要多少精力）。课堂的投票正好对应这三条：诊断线上故障、迁移 API 错误可回滚且可验证，倾向自主；发五万封营销邮件不可撤回，报税与调药错误代价极高，倾向先问或禁止。

**4. 如果一个能力既可以通过训练获得，也可以通过脚手架获得，你会根据什么做选择？**

参考答案：看四点：(1) **普遍性与稳定性**——问题是否跨任务反复出现，训练内化才有回报；(2) **能否被外部产物承载**——提示、工具、记忆这类脚手架可移植、人类可读可改，而权重只对该模型有效；(3) **时间与数据成本**——训练周期长、需要大量高质量轨迹，脚手架当天就能迭代；(4) **是否需要快速试错**。课程的判断是实践中先在脚手架侧解决，等训练方确认问题足够普遍再内化；长上下文这类还涉及效率的能力，会长期留在脚手架侧。

**5. 在 Hugging Face 事故中，四层防线分别对应系统里的哪个组件？**

参考答案：**沙箱**对应隔离执行组件（限制网络、文件系统与可访问目标）；**凭据限制**对应权限与凭据管理组件（模型只能拿到被授予的密钥）；**监控**对应可观测性组件（记录轨迹、耗时、异常并触发告警）；**安全护栏**对应训练目标与策略约束层（该模型正被训练用于攻击性测试，缺少阻止它越界的目标设定）。四层同时失效，才让「攻不进目标就改攻第三方」成为可能。
