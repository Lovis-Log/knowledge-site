## Three different things called "writing code"

1. **Single-step generation**: natural language in, a program out.
2. **Repository-level change**: read several files, fix an issue or add a feature.
3. **Full software development**: review, deployment, monitoring, maintenance, requirements.

This lecture focuses on the engineering behind the second and third. The third is often forgotten: a 2019 Microsoft survey found developers spend only about 15% of their time writing code, 25% in meetings and email, 14% debugging, and 8% running tests.

## What a model needs to write code

Single-step ability splits into three parts:

| Ability | Meaning |
| --- | --- |
| Language understanding | Knows the target language's syntax and idioms |
| Editing | Makes incremental changes rather than rewriting |
| Reasoning | Breaks a problem into verifiable steps |

Editing is not free. A model needs many before/after examples in training to change code reliably.

### Pre-training

Code must be in the corpus, but not only code — the model also needs to follow natural-language instructions. Details the lecture stresses:

- **Whitespace carries meaning**: Python indentation cannot be normalized away.
- **File boundaries**: the corpus must represent where files start and end.
- **Block structure**: Markdown code blocks must stay intact.
- **API and documentation relationships**: code should appear alongside text explaining it.

### Data cleaning

Code has an unusual distribution, so cleaning is harder than for text:

- filter by language and source, removing autogenerated code, broken encodings, and low-value repetition;
- **deduplicate aggressively**: GitHub contains enormous numbers of forks, vendored libraries, near-identical files, and copied solutions;
- record licenses, source dates, opt-outs, and filter sensitive data. Leaked API keys are common; tools such as TruffleHog scan for them.

### Tokenization

Any subword method works, but code imposes two requirements:

1. **Preserve whitespace**, or indentation information is lost.
2. **Compress frequent spans**, such as several levels of indentation plus a newline.

Allowing tokens to cross whitespace yields a more compact representation (about 40% fewer tokens) but can produce very long tokens — `import numpy as np` as a single unit — which prevents mid-line completion. There is a trade-off.

Models also have strong language biases: without a specified language, most tasks become Python, while dashboards become React. The bias comes from ease of writing, popularity, and the interpreter used during RL.

## Mid-training: turning a general model into a coding model

The public reports from Code Llama and Qwen2.5-Coder give two lessons:

1. **Raise the code share, but not to 100%.** Qwen2.5-Coder found that training on pure code hurt math and question answering significantly; mixing text and math kept general ability with only a small code regression.
2. **Extend context.** Repositories often exceed a million tokens, so simply concatenating files does not work. Options include grouping by directory or following the dependency graph to keep related files together. Qwen2.5-Coder trained from 8K up to 128K using YaRN-style extension.

### Fill-in-the-middle training

A plain autoregressive model sees only the left context, but editor completion happens in the middle:

```python
def is_positive(x):  # infer the return type here
    return x > 0
```

From the left alone, `is_positive` could return bool, a string, or an enum; the right side settles it.

FIM rewrites the task as autoregressive generation: provide prefix and suffix, mark the hole with sentinel tokens, and generate the middle. At inference the sentinel sits between prefix and suffix. Multiple holes use multiple sentinels.

This supports file-middle completion, type inference, comment generation, and variable renaming. The cited results show FIM-trained models far outperform left-to-right generation with reranking on middle completion, without losing ordinary completion ability.

## What else code can teach

| Source | What it teaches |
| --- | --- |
| Commit diffs | From "before + commit message" to "after" |
| Diagnostics and repairs | Broken code plus an error to a fix; CI logs are public and rich |
| Execution traces | Instrument the program and observe state at runtime |
| Agent rollouts | Let an agent attempt tasks and record trajectories |

CI deserves emphasis: a version fails, a later version passes and merges, and the whole history is public on GitHub. Almost no manual construction is required.

## Evaluating generated code

### Comparison with a reference

BLEU-style metrics compare token and n-gram overlap, but `>=` and `>` differ by one token and behave differently; conversely, different but equivalent implementations score low.

Improvements:

- **CodeBLEU** compares abstract syntax trees and matches semantic data flow.
- **CodeBERTScore** embeds tokens and checks that every token has a counterpart in the other implementation.

These remain fragile and are now auxiliary signals.

### Execution-based evaluation

The mainstream approach runs unit tests: all pass gives 1, otherwise 0. It accepts any correct implementation, but writing good tests is extremely hard.

Two error types are common:

- **False positives**: tests are too weak and incorrect implementations pass.
- **False negatives**: the task description omits a requirement the test checks, such as a button's background color.

Isolation and dependencies also matter: Docker images preinstall packages, but upgrades break tests; running a large repository's suite can take minutes per example.

Common benchmarks include HumanEval (hand-written by OpenAI) and CodeContests (competitive programming), reported with pass@1 and pass@k.

Code quality, runtime efficiency, and maintainability were largely absent from non-agentic training rewards; work such as NoFun begins to score runtime, resource use, maintainability, and security.

### Reinforcement learning for single-step generation

With tests, RL is straightforward: sample responses, run tests, update on the result. This is a major reason reasoning models improved at competitive programming, where execution timeouts make efficiency part of the score.

## Agentic coding: localize, edit, verify

The standard loop for repository tasks:

1. **Localize** the place that needs changing;
2. **Edit** it;
3. **Verify** by running tests; on failure, use the error to return to step 1.

Agentless offers an alternative: predict the files, then classes and functions, then lines, and generate a patch with a single-step model. For a while it was surprisingly effective, because models were trained heavily for single-step resolution and less for tool calling and verification loops. Agents are now the norm.

### Is a single bash tool enough?

mini-swe-agent shows that bash alone can work:

- localization with `grep`, `ripgrep`, `cat`, `find`;
- editing with `sed`, one-off Python scripts, `patch`;
- verification with `pytest` and build commands.

But bash is a poor editing interface. Replacing text full of backslashes with `sed` invites escaping errors, and the model must choose among `sed`, Python, and `patch` each time.

Nearly every competitive coding agent adds a **dedicated file-editing tool** supporting whole-file writes or search-and-replace.

### Edit format matters more than expected

Two common formats:

- **Unified diff**: line-numbered and precise, but models frequently miscount lines.
- **Search-and-replace**: original text plus replacement, no line numbers, more robust.

Search-and-replace is ambiguous when the same `retries = 3` appears several times; the model must include more context to disambiguate. The overall win still favors it.

The Aider edit benchmark found GPT-4 Turbo much better at unified diffs, simply because it had seen more of them. Gemini later underperformed on many harnesses because it used its own edit format. **A mismatch between model and harness format becomes a major bottleneck.**

### Localizing code

The usual tools are `ripgrep`/`grep` plus reading along call chains. Work such as LOK Agent provides a dependency-path jumping tool, but the lecture's experience is that complex tools often lose to simple ones.

## Evaluation and training environments

### SWE-bench

Construction:

1. take a GitHub issue as the problem;
2. take the repository state before the issue was resolved as the starting point;
3. take the tests introduced with that issue as the check.

Apply the patch, run the tests, and score 1 if the relevant tests pass. Tests split into:

- **FAIL_TO_PASS**: fail before the fix and pass after, verifying the new behavior.
- **PASS_TO_PASS**: pass before and after, preventing regressions.

Running the full suite is too slow — Django or NumPy can take five to ten minutes per example — so a subset is selected.

A runnable task needs: starting files, dependencies, a test command, the issue text, and the checks.

### From evaluation set to training set

- **SWE-Gym** builds additional training environments in the SWE-bench style. A model at roughly 11% success improved noticeably after 500 examples; generating multiple outputs and reranking improved it further.
- **SWE-rebench** continuously generates environments from new pull requests (the lecture mentions December 2024 through June 2026), with train and development splits — currently one of the larger public coding-agent datasets.
- **SWE-smith** does not need pull requests. It mutates runnable code in the spirit of mutation testing, keeps the tests, injects bugs, and asks the model to repair them. Data is nearly unlimited and cheap, but less natural than real issues.

Multilingual versions (Multi-SWE-bench, SWE-bench Multilingual) mostly contend with differing language conventions, which agents now handle well.

### Multi-harness training

One model can perform very differently across harnesses because edit formats and tool protocols differ. Model providers therefore train on several harnesses; NVIDIA's Nemotron report mentions training on five or more.

## Beyond fixing issues

The inner loop is bug fixing, testing, and iteration. The outer loop includes review, deployment, monitoring, maintenance, and requirements.

Tasks and benchmarks that now exist:

- **Code review**: measure whether comments are adopted;
- **Front-end bug fixing**: SWE-bench Multimodal, verified with Playwright scripts or a GUI agent;
- **Building apps from scratch**: the hard part is validation;
- **Reimplementing binaries**: ProgramBench, reverse-engineering a binary and rebuilding it — long-horizon and difficult;
- **Many issues over time**: SWE Milestone, checking that a repository stays maintainable after repeated changes;
- **Test generation**: SWT, using mutation testing to judge whether tests catch real breakage;
- **Deployment and operations**: needs real infrastructure and lacks mature benchmarks.

A counterintuitive observation: GLM 5.2, not a multimodal model, ranked first on a front-end design arena. Front-end skill does not strictly require visual input, though multimodality still matters for most tasks.

## Takeaways

- Coding ability comes from pre-training data, cleaning, tokenization, long context, and mid-training together.
- Pure-code continued training damages general ability; mixed data is safer.
- FIM lets models complete the middle of code, enabling type inference and renaming.
- Execution-based tests are the main evaluation, and test quality is the biggest bottleneck.
- The agent loop is localize, edit, verify; the edit tool's format strongly affects success.
- SWE-bench defines success with FAIL_TO_PASS and PASS_TO_PASS; training environments can come from PRs, mutations, or agent rollouts.
- Software development extends far beyond the inner loop; review, deployment, and maintenance remain open problems.

## Check your understanding

**1. Why must Python whitespace not be normalized during pre-training?**

Reference answer: Python uses indentation to define block structure, so whitespace is **part of the grammar**, not layout. Collapsing whitespace or stripping indentation merges blocks that belong to different scopes, teaching the model a wrong mapping from syntax to meaning; generation then produces programs with different semantics. The same applies to file boundaries (how the start and end of a file are represented), keeping Markdown code blocks intact, and placing code next to the prose that explains it.

**2. How does FIM turn middle-filling into autoregressive generation, and what does it enable?**

Reference answer: The model is given a **prefix and a suffix**, with sentinel tokens marking the region to fill, and it generates the middle autoregressively as usual; at inference the sentinel sits between prefix and suffix. Several holes can be generated with several sentinels. It enables mid-file completion (where editor completions usually happen), type inference (the return type of `return x > 0` needs the right-hand context), docstring generation and variable renaming. Models trained with FIM are far better at mid-file completion than "generate left-to-right then rearrange", without losing ordinary completion ability.

**3. What are the two error types in execution-based evaluation, and why is test quality the current bottleneck?**

Reference answer: **False positives** — the tests are too weak, so a wrong implementation passes; **false negatives** — the tests check something the requirements never stated (a button's background colour), so a correct model is marked wrong. Test quality is the bottleneck because the entire evaluation rests on the tests: weak tests pass wrong code, incomplete tests fail right code, and add to that Docker isolation, dependency upgrades that break tests, and several minutes per run on large repositories. Writing good tests is the hardest part to scale.

**4. Why do most coding agents add a dedicated editing tool to bash? How is search-and-replace ambiguity resolved?**

Reference answer: bash is a poor editing interface — `sed` replacements with many backslashes are easy to escape wrongly, and the model must choose among `sed`, a one-off Python script and `patch` each time. A dedicated tool supporting whole-file writes or search-and-replace is more reliable. Search-and-replace is ambiguous when the same snippet occurs several times (multiple `retries = 3`): the model must include enough surrounding lines to identify one location. Compared with unified diffs, search-and-replace does not rely on counting line numbers and is generally steadier. A related lesson: **the model and the harness must agree on the edit format**, since a mismatch becomes a major bottleneck.

**5. What do FAIL_TO_PASS and PASS_TO_PASS each protect against?**

Reference answer: **FAIL_TO_PASS** tests fail before the fix and must pass after it, verifying that the feature or fix actually works — they prevent "scoring without changing anything". **PASS_TO_PASS** tests pass both before and after, guarding against regressions — they prevent "fixing this and breaking that". Together they require a patch both to solve the problem and to preserve existing behaviour.
